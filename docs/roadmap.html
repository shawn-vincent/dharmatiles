Where to start

The order these are best taken in. Each one is described in its section below.

  1. Rerun the slow tests and fix the OpenLOCK failure, so everything after starts from green.
  2. Per-entry rebuilds. Drafts are built, but still rebuild the whole tile. Keeping unaffected entries would make trees and control sweeps respond quickly.
  3. The editor, in the stages its design sets out: select, edit, drafts, place and draw (built), then hardening the editing experience and the gate's versions. The assistant is deliberately deferred.
  4. Lines with width= and along=, the language's biggest gap: paths, walls and streams that follow a drawn line.
  5. The first public release, once the licence for the library is decided.

The editor

The preview becomes the editor: one view in which you see a tile, select any part of it, change it, and place new things on it, with the document's text beside it. The design is The editor.

  • PlannedA full value editor for every control. Each value in the sheet can be written as a single number, a range (2..4) or an expression. A height offers the named levels (edge, water, the tile's own) in a list, and an expression is typed in place with the same completion as the text pane. Today the sheet only scrubs numbers.
  • PlannedA thin outline in place of the hover tint, so a hovered thing's own paint shows.
  • DesignedRebuild only what changed. Drafts work (see the preview) but build the whole tile, so a tile with a tree drafts in seconds. Keeping each entry's parts and rebuilding only the entries a change touches, or that read what it changed, would make every draft quick; each solid's id is reserved in order, so kept parts need their ids kept with them.
  • PlannedThe lens, further: words tried on hover, and each control's line from its element page on hover.
  • DesignedThe stack, further: what each entry reads and writes, drawn between rows on hover; dragging a row to move its node; definitions as rows that open. Placing, the map and muting work (see the preview).
  • DesignedOne layout for every screen: desktop, tablet and phone, mouse and touch.
  • DeferredAn assistant. The design remains: with your own API key, ask in words and review the proposed edit. Editing by hand is being made excellent first.
  • DesignedSeeds and sweeps: a strip of the same tile at other seeds, or across a range of one control, picked by clicking.
  • PlannedPer-entry rebuilds. Keep each stack entry's solids, keyed by what it read, and rebuild only the entries a change touches, then the union and the gate.
  • PlannedSmaller meshes. Indexed and quantised meshes for the view (a 2×2 grass tile is 140 MB sent whole today), needed before a view on another device.
  • PlannedSection cuts and measuring in the view.
  • IdeaSide by side: two builds of one tile, or two tiles, turned together.
  • PlannedChange the system without restarting (DungeonBlocks or OpenLOCK) from the view.
  • PlannedA desktop app that holds the same page and the program in one window (Tauri), then tablets and phones: view and edit first, building on the phone later.

The language

  • PlannedTerrain by regions with height. A substantial redesign of how hills, cliffs, regions and terrain are written. Hills come out of grass and ground's noise into their own shaped regions: height anchors at points, along lines and on region edges (taper to flat at the tile edge, meet the water), point magnets, ranges and seeded randomness. A cliff becomes an object that follows a path, with a height and a region of its own: a fixed top gives a flat-topped cliff, a varied top a jagged one, and the same anchors make spires. The surface stays a height field, solved from the anchors by a distance-weighted blend held under a slope limit; overhangs stay with solids.
  • PlannedA line's width=, and building along= a line. Walls, paths and streams that follow a drawn line. check already names such lines; build refuses them.
  • PlannedPlan, then build. An element that places things first and builds them later, so others can read the places in between. The reeds' ripple rings need it: the water is built before the reeds, and cannot yet ring them.
  • IdeaSeeds on every part. Each stack entry already has its own seed, keyed from the tile's by its path, and seed= pins one entry outright. The idea is to carry this all the way down: any part, a scatter's child or a piece inside a definition, can pin its own seed, so a part with a fixed seed looks the same wherever it is used. Whether a part with no pin should derive its seed from the nearest pinned parent rather than the tile stays open.
  • IdeaGrass that writes the surface. Let the soil dip 0.4 mm under grass. Grass is built after the lift today, so it cannot.
  • IdeaLift a small rock to show above grass. Grass already stands lower beside rocks; only rocks under about 3 mm would need it.

Elements

Controls the schema has and the build refuses

These are on their element pages, marked not built yet: check accepts them and build refuses them.

  • Plannedscatter: clumps (gather into clumps), mostly (skew every child's size), spread (a cluster round at=).
  • Plannedrock, stone, boulder, pebble: wear (crisp, or chipped and rounded edges).
  • Plannedcliff: the foot (bank-height, bank-reach, scree, boulders, grit) and the rock shape weights (columns, blocks, slabs, odd, monoliths).

Not built

  • Plannedwall: doors, windows and hatches; the mortar sheet behind the stones.
  • Plannedfloor: cracks engraved in the flags.

Built, to be improved

  • Plannedtree: the crown reads thin; leaves under the crown lie flat instead of hanging; the crown's width and its share of the 55–65° band are tight; the clumps' rounded undersides hang, so both library tree tiles fail the gate (about 142 mm² past 65° on a 1×1 tree, against 7.8); a tree builds slowly.
  • Ideagrass: rework the blades by the leaf method (what it must look like, then guarantees by construction, then iterations judged on renders).
  • Plannedcliff: some builds drop a hairline shard (at most 0.01 mm³; cause not found); the guard against thin fins is not built; the rubble at the foot is thin and the columns too tidy.

Targets not met

  • FailingThe OpenLOCK test. In the last full run one library tile failed the gate or the base checks when built for OpenLOCK. Find it and fix the geometry where it is made.
  • FailingNot rerun. The golden and OpenLOCK tests have not run since the code was cleaned up and renamed. Quick checks show identical builds; the full run is owed.
  • FailingDirt stones' relief. The 10–40 mm band of the relief spectrum is 1.203 times its target, against an allowance of ±20%.
  • FailingRock texture. The printable-texture score on the rocks tile is 88–93%; the target is 95–97%.

Printing and slicers

  • PlannedA file Bambu Studio cannot save over. Bambu Studio saves its project over the 3MF it opened, so the next build replaces your changes or your changes replace the build. Name each 3MF uniquely, or write the build somewhere Bambu Studio does not save.
  • PlannedOrcaSlicer and PrusaSlicer. Check that both keep the painting, and say so on Printing.
  • IdeaColours through Bambu Studio's import dialog: a plain 3MF variant that carries base-material colours and no painting, for people who want Bambu Studio to match colours to their filaments.
  • Needs ShawnA test print of the cliff, and of a painted 3MF on a multi-colour printer.

  • Needs ShawnPublish the first release: the macOS binary and a Homebrew formula are ready to build; publishing them is Shawn's.
  • PlannedLinux and Windows builds, and the same golden hashes on every system.
  • PlannedCI, once the builds are cross-platform. Until then the tests run on Shawn's Mac.
  • IdeaBuilding in a browser or on a phone. It needs a mesh library that compiles to WebAssembly. The pure-Rust port of Manifold does, but is slower in parallel today; measure it again on our tiles when this comes back.
