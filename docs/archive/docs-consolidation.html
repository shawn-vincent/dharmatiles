Pulling the docs into a tighter model

The docs site has grown to 114 text documents, about 52 of them reachable from the navigation, in 81 MB. Most of the sprawl is the same few subjects written up again by each wave of work: the Python library, then the labs, then the Rust study. I recommend one page per look, four pages for the Rust project, two for standards, and a frozen archive: about 17 maintained pages in place of 52.

The recommendation in one line. Organise by subject, not by when the work happened. Each look (grass, rocks, cliffs, …) gets one page that is its spec, its rulings, how it works, and its history. That same page is what the Rust port of that look is judged against. Everything that only records how we got here goes into an archive that nobody has to maintain.

What is wrong, ranked

  1. Three generations each re-describe the looks.
    • The Python library design pages describe code that the Rust cutover deletes.
    • The lab pages describe the looks that were approved.
    • The Rust study then summarises both again (library, labs, variants, mechanisms).
    No single page answers "what is grass supposed to be, and how is it made now?"
  2. History is mixed into pages that should describe the present.
    • 13 pages carry red "out of date" notes on top of the original text.
    • The overview opens with revision banners 2, 3 and 4.
    • Lab design pages are mostly iteration logs.
    • The changelog has 147 entries in 118 KB, larger than any page it describes.
    A reader has to filter out the past to find the present.
  3. The Rust study documents a decision process, not a design.
    • The architecture page still shows 15 crates; the layout page replaced them with 6.
    • The feasibility page lists risks that the spikes have since retired.
    • Go/no-go, R1/R2/R9, R3 and R6 each restate parts of the plan.
    • The KDL vocabulary is split between R6, the intuitiveness review and decisions D1–D12.
    Phase 1 has started, so most of that process is now finished history.
  4. Standards are scattered. Facts that every tile must obey sit in five different places:
    • tile, square and cell terminology;
    • DungeonBlocks heights;
    • OpenLOCK geometry;
    • edge coordinates;
    • the 55° overhang limit and printable-texture rule.
    Those places are CLAUDE.md, a guide, a reference page, a lab requirements page and memory.
  5. Hygiene.
    • An Emacs autosave (docs/grass/#grass-behavior.md#) is committed; a lock-file twin of it broke the first Pages build.
    • docs/memory/ is a June copy of the project memory, superseded by Claude's own memory, but CLAUDE.md still points to it.
    • There are two stylesheets (assets/docs.css and rust-rewrite/dt.css).
    • About 80 experiment renders (≈15 MB) are linked from nowhere.
    • 24 experiment .tile.py specs sit in docs/ instead of src/tiles/.

Under the three cards: one live status list (grouped by body of work), then the look index, which is where the three meet. Each look page says which body currently owns that look and where its port stands.

One template for every look page

The same seven sections in the same order, so the eight look pages read as a set:

  1. Target and rulings. The reference image, and what Shawn loved and rejected, with quotes. Today these are spread across lab requirements, labs.html and variants.html.
  2. Requirements. Testable, with the named failure modes. From the lab requirements page.
  3. How the approved version works. Pipeline, key tricks, parameters. From the lab design page, minus the iteration log.
  4. Printability guarantees. What is true by construction, and what the audit gate checks.
  5. Variant history, compact. The family tree from variants.html with one line per variant. Full logs go to the archive.
  6. References and renders. Links into reference/ and the current renders.
  7. Rust port. Phase, KDL vocabulary for this look, a link to its parity contact sheet, status.
This makes each look page the parity spec for the Rust port. The plan already judges each port against the labs over four seeds. The look page is where "what the lab does and why" lives in one place, so the port and the review read the same thing.

Rules that keep it tight

  1. A page is about one subject and describes the present. A new doc needs a slot in the model, or it becomes a section of an existing page.
  2. Stale means fix it or archive it. No more "out of date" notes on top of old text.
  3. History has one place. A short "History" section at the bottom of each page, plus archive/ and git. No revision banners at the top.
  4. Retire the changelog. Keep a decisions log on the plan: one line per decision, Shawn's quote and the date. Edits themselves are in git.
  5. Session logs and iteration logs are not docs. They go straight to the archive, or stay in the commit messages and the lab's out/.
  6. Images live next to the page that shows them. Renders that no page shows are not committed.
  7. One status for everything. status.json moves to the home page and covers the Rust phases and the lab rounds alike.
  8. One stylesheet, one nav, and the same nav on every page.

Questions for you

  1. Python library design pages: archive now, or keep them current until cutover? I recommend archiving now. The Python library is no longer where looks are developed, and trees and walls get their current content on the look pages.
  2. Delete the ≈80 unreferenced experiment renders? I recommend yes: git keeps them, and the archive keeps the logs that describe them.
  3. Retire the changelog in favour of a decisions log? I recommend yes.
  4. Who is the site for? Today it is a workbench for you and me. If tabletop users will read it later, the language page becomes the start of a user guide, and the looks pages get a gallery at the top.
  5. Is the pilot look right? I suggest cliffs. Ground comes first if you'd rather match the port order.
