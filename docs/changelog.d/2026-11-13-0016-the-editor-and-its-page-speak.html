• The editor and its page speak one contract: every call the page makes has one request type and one answer type in the program (crates/dharmatiles/src/preview/api.rs and calls.rs); a request with a field it does not take, or without one it needs (every edit names the docRev it was made against), is refused with a 400 that names the field, and no route builds its answer by hand. web/preview/js/api.d.ts is generated from those types and a test fails when it is stale; the page’s one request layer and the files that build requests are checked against it by tsc in npm test, so a field renamed in the program fails in the page’s own code. Every failure has one shape with an honest status: a document that does not read is a 422 with its mistakes (it was a 200 with ok: false), a refusal is JSON with its status (never plain text), and the page reads them one way (whyOf in problems.js). One field-name convention, camelCase, on the wire. Putting a tile on a list from a list you have open names that list’s revision.
