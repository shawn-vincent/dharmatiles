Phase 0 spikes

Five experiments that could have changed the Rust design: booleans at cliff scale, materials through booleans, determinism, rays without Embree, and the KDL tile format. All five are a go. This page records how each was measured and what it found. It is frozen: later measurements belong to the phase that makes them.

The five spikes

A spike is a short, time-boxed experiment that answers one risk question. Each had a go criterion, which keeps the plan as written, and a fallback for no-go. All five ran on 1 Nov 2026 on Shawn's M2 Max (12 cores) and in GitHub Actions on branch rust/p0. A fresh agent reviewed the results adversarially the same day; its 14 findings were re-measured and are folded into the numbers below. Shawn decided GO on 2 Nov 2026 (decisions log).

R1: booleans at scale

Question
Can a Rust Manifold binding replay the cliff's and the tree's booleans watertight, with Python's results, at Python's speed?
Method
Capture every boolean from rockpile (1×1 at seed 1, and the 2×2 massif) and from the 2×2 tree tile. Replay them in manifold-csg (parallel on and off) and in manifold-rust. Time box 4 days.
Go when
manifold-csg: every result watertight, volume within 1e-6 relative, the same triangle count, and time ≤ 1.2× Python. manifold-rust becomes the default only if it also matches original IDs and properties at ≤ 1.5× the time.
Fallback
Ship manifold-csg only and defer the browser build. If manifold-csg fails to build on a CI OS, vendor a prebuilt static library. If both fail at cliff scale, keep the cliff in Python longer and port everything else.
Verdict
go manifold-csg with Manifold's parallelism on. The time gate passes on the median, not on every run; P7 re-times the booleans on an idle machine. manifold-rust stays the browser backend.

A wrapper around manifold3d (tests/parity/capture/booleans.py) recorded every boolean the labs perform, with operands and results saved as meshes: +, -, ^, batch_boolean, trim_by_plane, split and split_by_plane. crates/dt-geom/examples/r1_replay.rs replays each one through the Mesh trait on either backend.

The rest is Python and numpy, which is where the port's speedups have to come from. The massif's largest op by input is a 58-part batch union of 13.23M triangles (largest operand 7.14M); its largest by part count is a 202-part batch union of 7.62M triangles.

What the capture does not cover. It records the seven boolean and plane calls above, and nothing else Manifold does. rockpile also calls refine_to_length, hull_points, simplify and extrude, and rocklab also uses refine_to_length; none of those were replayed (nor smooth_out, which feasibility listed), so R1 says nothing about their parity or speed in Rust. The cliff captures are from clifflab round 15 (3b56ae0); round 16 (ee42cb8, after the capture) added hull_points chips and a batch_boolean subtract, so the frozen P7 rockpile will do booleans R1 has not seen. No recapture was made.

The baseline is a Python replay, not the in-situ time

Two things made the in-situ numbers unusable as the yardstick. First, the three captures ran at the same time, so their timings are inflated. Second, a re-imported operand is not the same object as the in-memory one: replaying the captures in Python itself changes the triangle count on 448 of 4,800 rockpile results and 1,461 of 16,676 massif results. So the comparison is Rust against replay_py.py: the same .dtm inputs, re-imported the same way, timed the same way (the op plus forcing num_tri()). manifold-csg's C API cannot pass face IDs in, so its baseline drops them too.

What the replay does not carry: tolerance

Each .dtm file stores the operand's tolerance, but the first replays ignored it on both sides, so every operand came back at Manifold's default for its size (about 1e-12 × size; 3.9e-11 mm on a 35 mm part). In situ, many cliff operands carried about 1.2e-7 × size (4.29e-6 mm and 8.31e-6 mm on the largest): float32's epsilon, from meshes Python built in float32, kept by every later boolean (a result takes the larger of its operands' tolerances). That is why 16 intersections replay with a different volume from the in-situ result (4 on rockpile, 12 on the massif; massif op 878: 13.44 mm³ in situ, 3.62 mm³ replayed). The re-measurement tried to carry it (replay_py.py --tolerance, r1_replay --tolerance):

Cause and requirement. A MeshGL round trip cannot restore an in-memory solid's state: Python's import ignores the tolerance, set_tolerance re-simplifies the mesh at it (so triangle counts drift on a third of the massif results, and massif op 351 even comes back with a negative volume, −11.9 mm³, in Python and in manifold-csg alike), and the port's import sets epsilon as well as tolerance. It fixes one of the 16 volumes (rockpile op 462) and not the rest. So the replay shows what it was built to show, the two kernels agreeing on the same inputs, and not that a re-imported operand behaves like the in-situ one. The requirement on the Rust kernel is to carry tolerance through the pipeline as Python's history does: where Python builds a solid from float32 data, Rust must give it the same tolerance at creation (TriMesh::tolerance; manifold-csg can only apply it with set_tolerance), and from then on keep solids inside the kernel. Parity on near-degenerate intersections is then judged by P3 and P7's metrics, not by this replay.

The adversarial review found that the first report used only the second of three timing passes, in which Python always ran first. The first pass (one run each, sequential) had the massif at 51.39 s for manifold-csg against 36.05 s for Python, 1.43×, over the gate, and rockpile at 1.15×. What R1 turned up

  1. Parallel must be on. With Manifold built without TBB, manifold-csg takes 3.1–3.3× Python's time on rockpile and 3–5× on the massif. With TBB it matches. It is now on by default (manifold-parallel). Sequential and parallel builds also give different triangles on a handful of ops (2 of 4,800; 1 of 16,676), and the parallel build is the one that matches Python.
  2. manifold-csg cannot import face IDs or run transforms. The C API's MeshGL64 options carry runs, merge vectors and tangents only. For the replay this made no difference (counts still match Python given the same inputs), but it means a mesh that leaves Manifold and comes back loses its coplanar-face grouping. Keep solids inside the kernel between ops; do not round-trip through TriMesh.
  3. Original IDs come from a process-wide counter. Plane ops mint a new ID for their half-space, and parts made in parallel get IDs in scheduling order. The replay compares only IDs carried from operands; R2 shows the consequence for determinism.
  4. Original-ID mismatches are all edge cases. 11 of 21,570 results: 8 intersections whose result is a zero-volume sliver on one side and empty on the other (largest 1.2e-4 mm³), and 3 plane trims where one side kept the half-space's minted ID and the other did not. Harmless, but the audit should count zero-volume slivers.
  5. The parity harness must compare metrics, not bytes. Even same-engine, same-input results are byte-identical to Python only 74–92% of the time (version 3.5.3 against 3.5.1 and re-import order). Triangle counts and volumes match.
  6. The port is close but not there. Sequentially it matches the C++ kernel's speed (24.3 s against 22.9 s on rockpile), and its rayon build gave the same whole-run hash as its sequential build on both cliffs, confirming the bit-identical claim. But its parallelism buys 1.7× where TBB buys 3×; its batch_boolean folds left to right (101 s on rockpile until PortSolid::batch was changed to union smallest-first); and it tracks Manifold 3.5.4, so its triangulation differs from Python's 3.5.1 on 24 ops and is byte-identical to it on only about 15% of results.
  7. Tolerance is not carried by a mesh round trip (details). The Rust kernel must give solids the tolerance Python's history gives them, at creation, and keep them inside the kernel.
  8. A toolchain trap on this Mac (history: rustup was reinstalled natively on 1 Nov 2026). rustup here is the x86_64 build running under Rosetta. Through it, the cmake build of Manifold compiled x86_64 objects into an arm64 binary and failed to link. Calling the arm64 toolchain directly (~/.rustup/toolchains/1.99.1-aarch64-apple-darwin/bin first in PATH) fixed it. Reinstalling rustup natively would fix it for good.

R2 and R9 together: one source-ID rule

The adversarial review found that the two spikes' rules conflicted and that neither was in the API. R2's pipeline called as_original() on each trimmed rock before the batch, and as_original() on a part with more than one source collapses its original IDs into one and recomputes its face IDs (a manifold3d check: a union's run IDs [2, 5] became [8], face IDs changed), which cuts the (original ID, face ID) link R9 traces materials through. trim_by_plane also mints a new ID for its cut face from the process-wide counter, and nothing said what material a cut face gets. Mesh::batch did no re-IDing.

The fix is one rule in dt-geom (crates/dt-geom/src/source.rs):

  1. Reserve, then assign by index. Before parallel work, reserve one IdBlock (Mesh::reserve_ids) in sequence. Part i's IDs are fixed slots of it, so their order is the index order whichever thread builds the part.
  2. Relabel leaves, not combinations. A leaf the kernel made (a level set, an import) takes its slot with Mesh::with_original_id(id, face_base), the one allowed TriMesh round trip, before any material is recorded for it. Each slot has its own face-ID range. as_original is not used in pipelines.
  3. Cuts carry an ID we give them. Mesh::trim_by_plane_with_id intersects with a half-space box imported under the cut's slot, so the cut face never gets a counter ID.
  4. Materials live in a table (Materials), keyed by (original ID, face ID), filled from each leaf right after step 2 and merged in index order. Rule for cut faces: a cut face takes the material of the solid being cut (its base material), registered under the cut's ID.
  5. Combine in index order. batch_in_order checks in debug builds that the parts' source IDs are disjoint and ascend with the part index, then runs Mesh::batch.

crates/dt-geom/tests/determinism.rs now runs exactly that: 24 level-set rocks built in parallel, each relabelled, cut flat underneath (into the ground) and on top (a sawn face that stays visible), then batch-unioned with the ground slab, at 1, 4 and 16 rayon threads, twice each, with the kernel's ID counter shifted by a different amount before every run (so only the order of IDs can matter, not their values). Each rock's material field is moss above a line and stone below.

Found on the way: a port bug. With the first version of the rule (face IDs left as the import computed them), the port's batch union renumbered the face IDs of 8,141 of its 24,954 output triangles, so they no longer traced: when two sources share face ID values, some survive a large batch union with another face's number. Single unions and small batches were fine; the C++ kernel never did it. Giving each leaf its own face-ID range (IdBlock::face_base, 220 IDs per slot) fixed it. manifold-csg's C API cannot import face IDs, so on the C++ backend the ranges are ignored and the C++ kernel keeps sources apart itself. Limits for P1: about a million triangles per leaf and 4,096 slots per block, lifted by widening face IDs to 64 bits as MeshGL64 has them. Worth reporting upstream with the R3 -0.0 bug.

R2: determinism

Question
Can two builds of the same tile be byte-identical, across thread counts and machines?
Method
A test pipeline (noise, scatter, EDT, a boolean batch) run twice on one Mac at 1, 4 and 16 threads, and in CI on Linux and Windows. Every stage is hashed. Time box 3 days.
Go when
Byte-identical on one machine at every thread count. Cross-platform results are measured, and Shawn chooses the level.
Fallback
If one machine can't be made identical cheaply, the gate becomes metrics plus render review, with per-platform snapshots.
Verdict
go Identical at every thread count under the source-ID rule and with libm in seeded code. macOS and Linux match; Windows differs. Shawn chose level B on 2 Nov 2026: one golden hash set for macOS and Linux, Windows gated on metrics and renders.

crates/dt-geom/tests/determinism.rs: value-noise fBm on a 384² grid, keyed-seed scatter, an exact EDT (Felzenszwalb, rows and columns in parallel), then 24 level-set rocks built and cut in parallel and one batch union with the slab (under the source-ID rule above, with every output triangle traced to a material). A further hash covers a sin/exp stage to measure the platform maths library. Each stage is hashed at 1, 4 and 16 rayon threads, twice each.

What this pipeline is, and is not. It is a toy: 24 rocks and about 25,000 output triangles, chosen to exercise the stages a tile has, not a tile. Manifold's own parallelism is whatever the build has (on by default): the port's rayon follows the test's thread pool, so its internal parallelism varies with it; TBB (the C++ kernel) cannot be sized from the test, so on Linux CI the test is re-run under taskset on 1, 2 and 4 CPUs, from which oneTBB sizes its default pool. All 18 runs per backend gave one set of hashes (run 41364160189). TBB's actual thread count was not read back.

One machine

The first run failed: the final union differed between 1 and 4 threads on both backends while every rock was identical. The cause is Manifold's process-wide original-ID counter. Rocks built in parallel get IDs in scheduling order, and a boolean orders its output triangles by original ID. A first fix, as_original() in index order, broke material tracing (see R2 and R9 together); the source-ID rule replaces it. With it, every hash is identical at every thread count, debug and release, on both backends, with the ID counter shifted between runs.

The R1 replay adds a larger, weaker check: two runs each of all 4,800 rockpile and all 16,676 massif ops with TBB on gave the same whole-run hash (692c31a3… and f99638b2…). That is two runs of one build on one machine, with each op replayed alone from saved inputs; it is consistent with Manifold's parallel booleans being run-to-run stable here, but it does not test the scheduling Manifold issue #1177 describes in general.

Our own code is identical everywhere as long as it avoids the platform maths library; note that this includes macOS against Linux: R2's own sin/exp stage differs between Apple's libm and glibc, not only on Windows. Manifold, in both its C++ and Rust forms, is byte-identical between macOS-arm64 and Linux-x86_64 on this pipeline, and differs on Windows with the same triangle counts and full material tracing. The cause on Windows was not found; MSVC's sin/cos in the plane and level-set paths is a guess, not a measurement. The port also differs on Windows, so it is not only a C++ compiler matter. The C++ kernel and the port never agree byte for byte with each other (24,970 against 25,214 triangles), because the port tracks Manifold 3.5.4 and manifold-csg ships 3.5.3.

Level chosen: B (Shawn, 2 Nov 2026). On this evidence, byte-identical golden hashes look achievable for macOS and Linux together; Windows needs its own hashes or a metrics-plus-render gate. Because the evidence is one toy pipeline, the P1 hash gate is the real test: if real tiles split macOS from Linux, option B falls back to A. Seeded code paths should use the libm crate rather than std transcendental functions.

What R1, R2 and R9 changed in the plan

  1. Ship manifold-csg with Manifold's parallelism on. The design note "run each boolean single-threaded and many in parallel" is not needed for identity on one machine, and costs 3–4× on the cliff's big unions.
  2. Add a kernel rule: source IDs follow dt-geom::source: a reserved ID block assigned by part index, leaves relabelled with their own face-ID range, plane cuts with given IDs, materials in a table, index-order batches. Without it, output depends on thread scheduling (R2) or material tracing breaks (R9).
  3. Keep solids inside the kernel between ops; a TriMesh round trip through manifold-csg drops face IDs.
  4. The parity harness compares triangle counts, volumes and renders, not bytes, against a Python replay.
  5. R1 ran at a larger scale than planned: single meshes up to 7.1M triangles, a 58-part batch union of 13.2M triangles and a 202-part one of 7.6M on the massif, not 1.7M. The kill criterion (cliff batch within 2× Python) is met (worst pair 1.43×); the ≤ 1.2× time gate passes on the median and not on every pair.
  6. Carry tolerance as Python does (TriMesh::tolerance); parity on near-degenerate intersections is judged on metrics in P3 and P7.
  7. R2's cross-platform level: on the toy pipeline, macOS and Linux can share golden hashes; Windows cannot until the cause of its difference inside Manifold is found. The P1 hash gate on real tiles is the real test.
  8. manifold-rust stays behind the trait as the wasm backend (the browser build compiles), and is re-measured when Python moves to Manifold 3.5.4 and the port's parallel speed improves. The R1 replay is the re-test: r1_replay --backend port.

R3: rays without Embree

Question
Can a pure-Rust BVH replace Embree for the leaf placer's rays?
Method
Capture the leaf placer's ray batches from the 2×2 tree tile (and, as an extra, the cliff's relief, grain and dirt rays) and replay them through obvhs and parry3d. Time box 3 days.
Go when
Within 3× of Embree, at least 99.9% of hits identical and the rest within 1e-4 mm, and a deterministic BVH build.
Fallback
embree3 over FFI as a native-only feature of dt-geom.
Verdict
go obvhs 0.4 with Embree's triangle test and medium_build; parry3d is the spare. The distance clause is relaxed to 1e-3 mm, because 1e-4 mm is tighter than float32 data allows. The fallback is dropped.

What was measured

tests/parity/capture/rays.py wraps trimesh's embreex layer (_EmbreeWrap) from outside and records every scene and ray batch exactly as Embree saw them: float32 vertices in trimesh's scaled frame, float32 origins and directions, and Embree's primID and tfar. It captured two builds:

  • Leaf placer: 2x2-grass-tree.tile.py at DungeonBlocks scale, built in memory (no STL written). 1,875 leaves placed; 80 scenes, 138,670 triangles, 465,164 rays, all from placement_leaf and placement_organic.
  • Cliff: clifflab/rockpile.py 1×1 seed 1, from this branch's copy. 175 scenes up to 2.6 M triangles, 11.4 M triangles in all, 18.4 M rays: _relief 16.3 M, _grain 2.1 M, _dirt_layer 19.6 k.

crates/dt-geom/examples/r3_rays.rs replays them in the same frame. Embree's times come from the same capture replayed through embreex 4.4. Embree builds with TBB on all cores, and embreex queries on one thread, so the build ratio compares multi-threaded builds and the query ratio compares single threads. Timings are the best of 5 runs for the tree and of 1 for the cliff.

Deterministic means the structure hash is equal at 1, 4 and 16 threads and across runs, and the 12-thread query returns exactly the 1-thread answers. On 12 threads, the queries run in 0.41–0.44× Embree's single-threaded time.

1. An obvhs bug, worked around

Unpatched obvhs lost 8.6 M of the relief rays. Those rays are horizontal, built as -cos(a)·m − sin(a)·z with a = 0, so their z component is -0.0. obvhs 0.4's safe_inverse(-0.0) returns -1/ε, but its octant test reads -0.0 < 0 as false. The slab bounds swap, and the ray misses every node. ObvhsRays adds +0.0 to each direction component, which turns -0.0 into +0.0 and changes nothing else. A unit test covers it. The bug should go upstream.

2. What is left is rounding on grazing rays

A referee in r3_rays.rs re-casts a sample of the disagreeing rays by brute force (every triangle, a Rust port of Embree's triangle test, no BVH), then nudges each origin by 1e-4 mm in six directions and re-casts the nudged rays the same way, to see whether the answer changes. Embree itself was not re-run on the nudged rays. The sample is 385 of the 20,762 far and hit-vs-miss disagreements for obvhs medium (about 1.9%); the 0.73% of rays that are ties within 1e-4 mm were not refereed.

What R3 changed in the plan

  1. R3 is retired for the leaf placer, with the distance clause relaxed to 1e-3 mm (see three captures). The trees phase can rely on obvhs behind Rays. Measured again on 1 Nov 2026 (2×2-grass-tree, both systems, 3 runs): leaf placement takes 3.4–4.0 s per scale, 7.1–7.7 s of a 17.2–18.3 s tile build (median 17.6 s), not the 11.3 s of Embree time quoted in feasibility.
  2. The cliff port should not cast exactly grazing rays. rockpile's _relief grid lines up with the mesh it casts at, so about 0.8% of its answers are rounding noise (their answers flip under a 1e-4 mm nudge in a brute-force re-cast with a port of Embree's test). In Rust, offset the grid off the mesh's own lattice (as overhang_faces already does) or use the depth-peel raster suggested in feasibility. Cliff parity is then judged on metrics and renders, not on ray-for-ray agreement.
  3. Every direction vector goes through Rays. The -0.0 workaround lives in ObvhsRays. No caller should use obvhs directly.
  4. Parallel speed comes from queries, not builds. Batch queries scale 6–7× on 12 threads. obvhs builds don't scale at these sizes, and they are already faster than Embree's.

R6: the tile format

Question
Can KDL carry real tiles without losing anything, survive machine edits, and read well to Shawn?
Method
Write 2x2-grass-tree, 1x1-wall-fieldstone-corner and a rockpile 2x1-cliff-run in KDL v2 under library/tiles/, with shared parts in library/parts/. Decode them into a draft model in a new dt-doc crate. Edit one control with the kdl crate. Time box 3 days.
Go when
Nothing in the tile is lost. Comments and layout survive the edit byte for byte outside the edited node. Shawn says they could write them.
Fallback
Change the syntax before P1. As a last resort, use TOML with toml_edit.
Verdict
go The format holds. Shawn found the approach right but the first parameters unintuitive, so the syntax and vocabulary were decided on 1 Nov 2026 (eight syntax questions, then ten vocabulary recommendations) and dt-doc was reworked to them as P1 stream A.

Results

  • Parsing and printing. The kdl crate 6.7.1 (KDL v2, its v1 features off) parsed every file and printed each back byte-identical.
  • Edits. An edit to one control changed only that value's own text. The spike's edit API could only replace values already written; insertion was P1 work and is now done.
  • Nothing lost. dt-doc, decoded by hand with byte spans on every name and value, asserted every value the Python tiles set. 35 tests passed, and the crate built for wasm32-unknown-unknown.
  • Errors. miette errors point at the text with a hint and keep going past the first mistake. Generic KDL parse messages are rewritten to say what to write (a forgotten quote, a misspelt control).
  • Two KDL v2 lessons. Ranges and percents must be quoted, because KDL numbers cannot contain .. or %. Switches are #true and #false.
  • Look decisions surfaced by the rewrite. No grass-carpet look (3D blades instead), grass moved last in the stack, which side of a line a wall sits on, and the cliff grown from a tile edge.
  • Gaps left for later phases. Meadow needs the species controls the tiles set (length, curl, clearance, clumps) or a ruling that they go (P4). cliff along=… must either be limited to tile edges or rockpile's band forms generalised to any line (P7).

The results above were measured on the draft vocabulary; the parts that do not depend on the words carry over. The decided vocabulary, the example tiles and every decision are on the language page (decisions).

The parity harness, Python half

Built during Phase 0 so the first look port could be judged from day one.

tests/parity/run_lab.py builds dirtlab 2×2 at seeds 1–4. For each seed it writes the STL, a metrics.json, and four renders (painted, top, low, 20 mm close-up) with overhang faces painted red, using clifflab's layer-reach audit at 55°. It finishes with one contact sheet. Output goes to out/parity/dirt/, which is gitignored. It renders through dharmatiles.render and falls back to a CPU Embree renderer with the same camera and lights when pyrender has no screen; this run used the fallback. A full run takes 95 s.
