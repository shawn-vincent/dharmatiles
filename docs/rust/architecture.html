How the Rust engine is built

A tile is a short KDL document that names built-in looks. A Rust engine builds each look once, from about twenty shared operations, and writes one audited, printable mesh. This page describes that engine: its six crates, its operations and kernels, how a build runs, and the risks still open.

1. What the engine does

There are two layers.

  • Documents. A tile is a KDL file. It names built-in looks (ground, dirt, grass, rocks, cliff, wall, tree, …) and tunes them with plain controls. It has no loops and no code. The language is on the language page.
  • The engine. Each look is a few hundred lines of Rust written against a shared kit of operations. The kit is where the old code's duplication collapses: about seventy separate mechanisms in the Python library and the labs become about twenty operations.

Why two layers and not one: the approved looks are solvers with dozens of tuned internal constants. The meadow has fifteen rim-steering constants; the cliff has dozens of guard and seat rules. Putting those in documents would make every tile a program. Keeping them inside a look, behind a control such as cover="80%", keeps documents declarative, which is what Shawn asked for: a static definition file… declarative.

The smallest real tile, library/tiles/test/flat-1x1.kdl, is the one Phase 1 builds end to end:

tile flat size="1x1" seed=1 {
    about "Flat ground at 5 mm on one square: the first tile built end to end."
    stack {
        ground          // flat, at the ground level (5 mm)
    }
}

Rules that hold for every tile without being written:

  • The printer profile (library/printers/default.kdl): 0.45 mm lines, 0.2 mm layers, 55° overhang, 0.2 mm gaps. Looks read it and build printable shapes by construction. See Printing.
  • The edge contract, so that neighbouring tiles butt: one ground edge level, a water tide that is calm at the edges, line anchors at fixed edge positions, a standard cliff end section.
  • The connector: the DungeonBlocks or OpenLOCK underside, built last. See Tile system.
  • Materials: every solid carries a material name that survives booleans, so colour can be added later without redesign.

2. Six crates

A crate is Rust's unit of compilation: one library or one program, with its own Cargo.toml. The workspace has six, under crates/. Each boundary is there because it buys something specific.

CrateHoldsThe boundary pays because
dt-geomThe kernels: f32 grids (lift, distance transform), rasterising and the paint bucket, meshes behind one Mesh trait, rays behind one Rays trait, path-keyed seeds, and the source-ID rule (crates/dt-geom/src/lib.rs).It holds every native or swappable dependency. The Manifold backend is a feature here and nowhere else. It changes rarely, so edits above it do not rebuild it.
dt-kitThe scene of tagged solids and its queries, the shared operations, the audit gate, the STL writer with its build record, and a CPU preview renderer (crates/dt-kit/src/lib.rs).It is the vocabulary looks are written in. The servers are thin wrappers over dt-eval, so separate crates would add boundaries that buy nothing.

Later members: app/src-tauri (the Tauri GUI; a workspace member but not a default member, so cargo build never compiles a webview), dt-wasm (wasm-bindgen exports: check, plan, build, render) and, only if a parity test needs it, dt-py (a PyO3 module exposing kernels to the Python labs).

Two places where the code differs from the first sketch. dt-looks does not depend on dt-doc: a look takes plain controls, and dt-eval translates the document into them. And in Phase 1, dt-eval still reads documents through a thin adapter (crates/dt-eval/src/doc.rs) that decodes the decided vocabulary directly; re-pointing it at dt-doc's model changes nothing downstream.

Rejected: one crate with modules (the document model would need Manifold to compile, and every edit rebuilds everything); a crate per kernel (four crates that always change together); separate crates for MCP and the language server (they only call dt-eval and dt-doc).

3. The kit: values, operations, contracts

The kit has three parts. Values are what operations pass to each other. Operations are what looks are written with. Contracts hold everywhere without being asked for.

Values

region
A paint-bucket area: named lines plus the tile edge, filled from one or more points.
field
A grid of values over the plane or a face frame: noise, distance, flow.
points
Placements with a radius and attributes such as size or kind.
curves
Lines, paths, networks and attributed graphs.
solid
A manifold mesh with a material, a kind (rock, wall…) and the path of the entry that made it.

Contracts

seed tree
Every call's seed comes from its stable name, never its position or a shared stream.
printer
Looks read the profile and build printable shapes; one audit gates the result.
material
Material names survive booleans through Manifold's original IDs.

The operations. The budget is about 22 over the whole project. Phase 1 has 12 of them (marked P1); the rest arrive with the first look that needs them.

Each look combines between one and ten operations, together with its own tuned constants. The operations are shared; each look is still its own solver. Four pairs looked alike on paper and are not, which is why the list has more than seven entries:

  • Stroke blades are layers, not a sweep. Each 0.2 mm layer is its own 2D stroke over a different span of the spine, a whole number of 0.45 mm lines wide (grasslab/grasslab.py:812–911). Hence loft has a layer-stack mode.
  • A gravity stack is not wall courses. The cliff picks the lowest unfilled cell and grows a stone into it (clifflab/rockpile.py); wall courses split a known rectangle with no gravity (src/dharmatiles/walls/masonry.py:286–365). Hence partition has three methods.
  • Face relief is not grain. Relief rasterises a face, clamps it and subtracts it; grain refines a mesh and moves vertices (rocklab/rocklab.py:283).
  • Swell is a solver, not relief. Water is a look built from field operations and fill; only its last step displaces a surface (waterlab/waterlab.py:719–944).

Kept from the Python library because it already works: paint-bucket regions, an ordered stack, distributions such as "6..8" on any number, a floor as a wall laid flat, the smooth-max block kernel, the crack network drawn first, the opening fit solver, the organic leaf placer, and guarantees by construction.

4. Kernels

A kernel is the low-level geometry code the kit sits on. There are four, all in dt-geom. Each external crate sits behind a trait so it can be swapped or vendored.

KernelWhat it isBuilt on
Gridf32 fields on one grid convention: lift, distance transform, morphology, blur. Ground, water, dirt, cliff support, seats and face relief all stay grids until the last moment.Our own code (crates/dt-geom/src/grid.rs: lift at :94, distance at :161). EDT, labels, blur and Poisson sampling are 50–150 lines each, and owning them keeps them deterministic.
Plan (2D)Line rasterising and the paint bucket now; polygons, offsets and Voronoi as looks need them.crates/dt-geom/src/raster.rs (fill at :86); Manifold CrossSection for anything extruded; i_overlay or geo, spade (Delaunay, Voronoi), kiddo (kd-trees) later.
MeshBooleans, hull, extrude, slice, refine, simplify, level sets. One Mesh trait (crates/dt-geom/src/mesh.rs:271).manifold-csg 0.4.1 (Manifold 3.5.3 in C++) by default, with Manifold's parallelism on. manifold-rust 0.19.2 (a pure-Rust port) is the wasm backend.
RaysA BVH for leaf seats and cliff tops. One Rays trait (crates/dt-geom/src/rays.rs:50).obvhs 0.4 with Embree's triangle test; parry3d 0.31 as the spare. Every ray goes through our wrapper, which fixes obvhs's −0.0 direction bug.

Kernel rules that came out of the Phase 0 spikes:

  • Keep solids inside the kernel between operations. A round trip through a plain triangle mesh loses face IDs (manifold-csg cannot pass them back in), and with them the material chain.
  • Carry tolerance as Python does. A solid gets its tolerance when it is created and keeps it, because a mesh round trip resets it and changes near-degenerate intersections.
  • One source-ID rule for determinism and materials; see Determinism.
  • For cliff face depth, use a depth-peel raster or offset the relief grid off the mesh lattice, rather than exactly grazing rays, whose answers are rounding noise.

Watertightness comes in three layers. By construction: lift, loft and convex carving make closed solids without booleans. By kernel: Manifold returns a manifold result for manifold inputs. At export: the audit gate (section 7).

5. A build, step by step

The labs exposed an ordering puzzle a single bottom-to-top pass cannot solve. Rocks in a meadow must claim their footprints before the grass grows, so blades steer around them. They must also be seated after the grass, so each rock rises above the grass top (meadowlab/meadowlab.py:224 then :236). So a build has two passes: first everything says what it writes and reads, then everything is built.

  1. Read. dt-eval finds the project (the nearest folder with a dharmatiles.kdl, as Cargo finds Cargo.toml), reads the document and its use imports through the source trait, and checks every name and value.
  2. Plan. Each stack entry says what it writes and what it reads (Look::plan). The scheduler orders the steps from that, not from where they are listed (crates/dt-eval/src/plan.rs):
    1. surfaces, painted in stack order (order decides which surface paints over which);
    2. the lift of the painted surface into the ground solid;
    3. solids, each after every writer of what it reads; the connector, which reads every solid, comes last.
    A read that nothing writes, a cycle, or a surface that reads a solid is refused here, before anything is built, with an error at the text that caused it.
  3. Build. Each step builds into the scene. Each entry gets its area (the whole tile unless in= names a region), its path, and a seed keyed by that path.
  4. Combine. The scene's solids are unioned once, keeping each triangle's material.
  5. Audit. The gate checks the mesh as a slicer sees it (crates/dt-kit/src/audit.rs:122).
  6. Write. The STL, a .build.json beside it, and painted preview PNGs on request.

The plan pass is cheap: 2D work and fields, well under a second. That makes it the live preview while editing. Plans are computed for everything up front; solids are built once and cached by (path, seed, hash of inputs). Most real operations are global (Poisson saturation, gravity stacking, geodesic distance), so building on demand point by point would recompute the world.

Two engine rules that are not syntax:

  • Below zero belongs to the connector. Carves may go below 0 (pits, stairs down). They are recorded and applied to the connector, which is built last because the DungeonBlocks peg height depends on the content's height.
  • OpenLOCK is a second evaluation, not a parameter. A 25.4 mm build changes footprints and densities. With position-keyed noise and path seeds, both builds share one layout.

6. Determinism

The level is B, decided 2 Nov 2026: one set of golden byte hashes, shared by the macOS and Linux CI jobs. Windows runs the thread-identity test, the golden summaries' metrics (triangle count, volume, overhang, holes) and the render gate, but not the byte hashes, because Manifold's output differs on Windows for a cause not yet found. See the plan for the decision.

  • Seeds by path, not by stream. Each key is hashed with 64-bit FNV-1a, xored into the parent seed and mixed with SplitMix64 (crates/dt-geom/src/seed.rs:23). An entry's path is tile/<name>/<look>/<k>, where k counts same-named entries (crates/dt-eval/src/lib.rs:392), so adding an entry of another look rerolls nothing else. Any entry may pin seed=. Nothing uses rand::StdRng, whose stream is not stable across versions.
  • The source-ID rule (crates/dt-geom/src/source.rs:46). Manifold numbers parts with a process-wide counter, so parts built in parallel would get IDs in scheduling order. Instead, reserve a block of original IDs and assign them by part index: each leaf solid takes a slot and its own face-ID range, plane cuts take IDs from the block, cut faces take the material of the solid cut, materials live in a table keyed by (original ID, face ID), and parts combine with batch_in_order (:206).
  • libm, not std, for sin, exp and powf in seeded code. The platform maths library gave three different hashes on three platforms.
  • Order-dependent solvers run in sequence within their entry (the gravity partition, the crack network, the coverage filler, the leaf standoff stack). Independent items (blades, stones, rocks) run in parallel. Reductions combine in fixed chunks in index order.
  • Manifold's parallelism stays on. It is 3–5× faster on the cliff, and its output was identical run to run on one machine.
  • Pin versions. The Rust toolchain (rust-toolchain.toml: 1.99.1) and the Manifold version are part of the output. Bump them on purpose, with the golden hashes as the check.
  • Position-keyed noise. The Python library draws noise per grid cell, so the same seed gives a different tile at a different resolution. The kit keys noise by position.

7. Testing and the audit gate

The audit gate runs on every build (crates/dt-kit/src/audit.rs). In order: separate pinches; quantise to float32 and merge vertices by position (what the STL reload will see); split into bodies and keep the largest, reporting what was dropped; then check watertightness, overhang area (the layer-reach rule at 55°, from rockpile) and see-through holes on what is written. A failed gate still writes the STL, exits with code 3, and paints overhang faces red in the preview. The policy is on Printing.

CI (.github/workflows/rust.yml) runs on every push: cargo fmt --check, Clippy with warnings as errors, tests on macOS, Linux and Windows, the thread-determinism test on both backends, the golden hashes, the parity harness on the flat tile, cargo deny, and three wasm checks: dt-geom built with manifold-rust, dt-doc checked, and dt-eval checked with --no-default-features --features manifold-rust. The last fails the moment someone adds std::fs or a native-only dependency to the core.

8. Front ends

All front ends call dt-eval. None shells out to another.

The command line

One program, dharmatiles, with subcommands, in the shape of cargo or gh. Shawn asked for a real command line, but using all the cool kid stuff like colors and… progress bars, not a full-screen text UI.

  • Now: build (with --png for painted previews and --json) and check (validate and plan, no geometry).
  • Later: watch, preview, audit file.stl, looks [name], init, paths, cache clean, completions, mcp, and eventually lsp.
  • Results go to stdout; progress, colour and errors go to stderr. --json prints one JSON report. Errors show the line, a caret under the mistake, and a hint (miette).
  • Exit codes: 0 success; 1 a bad document or failed build; 2 usage error; 3 built, but the audit gate failed (crates/dharmatiles/src/main.rs).

MCP server

dharmatiles mcp over stdio, using the official Rust SDK (rmcp); Streamable HTTP later. The agent edits KDL with its own file tools and calls ours: check_document, list_looks, describe_look, list_tiles, build_tile, render_preview (a PNG with overhangs red, from dt-kit's renderer) and audit_mesh. Tool inputs use the same schema dt-doc derives for the GUI, so there is one contract.

GUI and live preview

A Tauri 2 app with a web front end and three.js for the viewport. The same front end runs on desktop, on phones, and in any browser through dharmatiles preview: one UI for three hosts. Live preview: the notify crate watches files, dt-eval rebuilds only the entries whose inputs changed, pushes the plan pass first (under a second), then each entry's mesh as a binary buffer.

Browser and phones

Everything except the C++ mesh kernel is pure Rust and compiles for wasm32-unknown-unknown. The browser build uses manifold-rust; CI already builds dt-geom that way. Phones start as a viewer and editor through Tauri mobile; builds on the phone can follow once the pure-Rust Manifold is proven there.

9. Repository layout and paths

One Cargo workspace at the repo root, beside the Python. The root Cargo.toml is a virtual manifest: it lists the crates and shared settings but is not a crate itself. Cargo ignores folders that are not members, and Python ignores crates/.

  • The library ships inside the program. crates/dt-eval/build.rs walks library/ and embeds every .kdl file, so one binary carries the library and works in wasm and mobile sandboxes. Documents address it with an explicit lib: prefix; relative paths mean your project. Nothing is resolved by search order.
  • Project file. dharmatiles.kdl is optional. It marks the project root and names the output folder. Without one, dharmatiles build file.kdl works with defaults.
  • Output. out/ beside the project file, mirrored by system and path below tiles/: lib:tiles/test/flat-1x1.kdl builds to out/db/test/flat-1x1-db.stl. Python keeps writing stl/, so a side-by-side comparison is two folders.
  • Porting the tiles. Each src/tiles/**/*.tile.py is rewritten by hand as library/tiles/<family>/<name>.kdl in the phase that ports its looks, and deleted once its KDL twin passes review. At cutover the Python is removed and kept in git history under a tag.
  • Settings. [workspace.dependencies] states every external version once. [workspace.lints] forbids unsafe in our code. Dependencies build at opt-level = 3 even in debug, because geometry at opt-level 0 is too slow to judge by eye.

Appendix: build provenance

Every build can say exactly where it came from, without access to git at run time. The engine captures its version once, at compile time, and every output carries it.

Capture

crates/dharmatiles/build.rs runs before compilation. It calls git describe --tags --long --always and git status --porcelain, and sets the DT_ENGINE_VERSION environment variable for the compiler. It reruns whenever HEAD or the index changes. The format matches the Python library's src/dharmatiles/build_info.py:

Source treeVersion
On a tagv1.0.0
Commits past a tagv1.0.0-12-gabc1234
No tag reachablegabc1234
Any of these with uncommitted changesthe same, plus -dirty
Built without gitunknown

dharmatiles --version prints it.

The build record

Each build makes a BuildRecord (crates/dt-kit/src/stl.rs:9): the engine version, the document path (such as lib:tiles/test/flat-1x1.kdl), a 64-bit FNV-1a hash of the document's text, the root seed, and the system (db or ol). It goes to two places:

  • The STL header. The 80-byte header holds one line: dharmatiles <engine> <system> seed=<n> doc=<hash> <path>, padded with spaces. It never starts with solid, which would mark an ASCII STL (stl.rs:27).
  • A .build.json beside the STL. The full record, the audit (triangles, vertices, volume, watertight, bodies, what was dropped, pinches moved, overhang mm², holes, failures), every stage hash, and the build time in seconds.

Two builds with the same record and the same stage hashes are the same build. A -dirty version means the source tree had uncommitted changes, so the build may not be reproducible from git alone. A wall-clock build timestamp is deliberately left out of the STL, because it would break byte-identical output; the .build.json carries the time a build took, not when it ran.

History

This design came out of the Rust rewrite study of 1–2 November 2026. A first draft had documents written directly in seven verbs; walking each lab through them showed that every lab needed extra constructs and two verbs merged mechanisms that really differ, so the verbs moved inside the engine and documents name looks instead. A fifteen-crate sketch was cut to the six above. The Phase 0 spikes then replaced assumptions with measurements: the backend choices, the source-ID rule, the libm rule, and determinism level B.

The full analysis is archived: the Python library, the labs, surface variants, mechanisms, the research notes (sources and dates for every crate version) and the change log. The phases and decisions are on the plan.
