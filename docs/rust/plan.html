The Rust plan

How the Python library and the seven labs become one Rust engine with a KDL tile language. Nine phases, three work streams, and about 32 weeks on the critical path (25 to 40 is the honest range). Every phase ends with something Shawn can print, and no look counts as ported until Shawn judges its renders equal to the lab's, side by side, over four seeds. Phases 0 to 2 are done (2 Nov 2026): the Rust engine prints a flat tile and builds dirt that Shawn judged equal to the lab. Phase 3 (rocks and water) and Phase 5 (walls, floors, bases and trees) are under way; live status is on the home page.

Why this plan

The study behind this plan read the library (20.6k lines), the seven labs (8.6k lines), every surface variant in git history and Shawn's rulings. Its findings that still drive the plan:

  • The labs set the look now, not the library. Port the labs first, and port the library only where no lab exists: regions, walls, floors, trees and bases.
  • Each approved look is its own solver built from shared parts. A tile names a look and tunes it with natural controls; the engine implements each look once, on about twenty shared operations (architecture). Today the same operations are written about seventy different ways.
  • "Plan, then build" solves the ordering the labs needed. Rocks in a meadow claim their footprints before the grass grows and are seated on it after.
  • Printability is a gate, not a report. Every look follows one recipe (large form, mid-scale structure, fine grain), and one audit at the end fails the build or warns loudly, with overhangs painted red.
  • The speedups are in grass and cliffs, not booleans. Python already runs its booleans in C++ (Manifold). Rust gains from parallel blades and adaptive heightfields.

The design is on the architecture page, the tile language on the language page, and the Phase 0 measurements on the spikes page.

How the phases depend on each other

The critical path

P0 (3) → P1 (3.5) → P2 (3) → P3 (6) → P4 (7) → P6 (1.5) → P7 (8) ≈ 32 weeks, finishing around mid-June 2027. If every phase lands at the short end of its range, that is 25 weeks; at the long end, 40. P5 has about four weeks of slack beside P4. The front-end stream is small and never on the path.

The real constraint is Shawn's review time, not agent throughput. Each look needs one or two rounds of side-by-side review, and some need a test print. So the plan never runs more than two look streams at once. If the review queue grows past two weeks, stream B pauses (see kill and pivot).

The faster schedule. If rockpile is frozen by about week 18, the cliff can start in stream B as soon as P5 ends. Then P7 no longer follows the cutover, and the total drops to about 26 weeks. Use the toggle above the timeline to see it.

The C++ Manifold build makes a cold run about 5 minutes (Windows is slowest) and a cached run about 1 minute; all three runner images ship cmake.

The KDL parsing approach

The kdl crate (KDL v2, format-preserving; 6.7.1 since R6, with its v1 features off) parses into a node tree, which dt-doc decodes by hand, with about one function per node type (tile, define, line, region, stack, and each look). Source spans are kept so miette can point at the mistake. There is no derive crate: knus needs co-maintainers and facet-kdl is young. Values go through one small hand-written expression parser covering arithmetic on parameters, ranges ("a..b", skewed with mostly=), named heights and field constructors. It has no loops, assignments or call chains. JSON Schema comes from the typed model through schemars, printed by dharmatiles schema and never committed.

The parity harness

It is built in P1, before any look is ported, and every look phase uses it. The harness never compares meshes byte for byte, because Python and Rust can't match that way (different RNGs, EDT tie-breaks and kd-tree order). R1 confirmed this even for the same engine on the same inputs: Python's Manifold (3.5.1) and manifold-csg's (3.5.3) agree byte for byte on only 74–92% of boolean results, and Python replaying its own saved operands changes about 9% of them, while triangle counts and volumes match. So where a kernel is compared directly, the baseline is a Python replay of the same saved inputs, and the comparison is on metrics. The harness compares what Shawn judges: numbers that describe the look, and painted renders side by side.

  • Same seeds: 1, 2, 3 and 4 for every look. These are lab seeds. Rust's path-derived seeds won't reproduce Python's random streams, so a seed means "the same test case", not "the same random tile".
  • Metrics: one set per look, computed by the same code from either STL (P0's run_lab.py already computes them from the STL alone): bare fraction, blade count and height range, rock count and size histogram, facet count, relief spectrum, wave amplitude, overhang mm², see-through holes, dropped bodies and time. Tolerance: within ±10% or within Python's own spread across the four seeds, whichever is wider.
  • Golden summaries (insta) per tile: stage hashes, triangle count, volume, overhang mm² and holes. cargo insta review shows what changed. STLs are never committed.
  • dt-py is not needed for this. The harness compares files, so it works with the labs exactly as they are. dt-py is built only if a kernel test needs Rust and Python on the same arrays.

Practices

Definition of done, per look

  1. Every library tile that uses the look has an approved KDL twin, and its .tile.py is deleted.
  2. The metrics are within tolerance over seeds 1 to 4.
  3. The printability gate passes: watertight after float32 reload, 0 see-through holes, overhang at or below budget and painted red in every render, and nothing dropped silently by keep-largest.
  4. Shawn signs off the Python-beside-Rust contact sheet as equal or better. This is the bar. Numbers alone never close a look.
  5. The look builds within its time budget, and its stage hashes are stable at 1, 4 and 16 threads.
  6. The look's controls show in dharmatiles looks <name> with units, ranges and defaults. Internal constants stay internal.
  7. The OpenLOCK build has been checked, from P5 on.
  8. A test print has passed where printability is at stake: water edges, grass tips, walls, trees and cliffs.
  9. A simplify review is done, and any decision it took is in the decisions log.

Adversarial reviews

Each phase exit gets one adversarial review by a fresh agent that has the code, the exit criteria and Shawn's rulings, but not the implementers' conclusions. It tries to break the claims: rerun the determinism checks, feed malformed documents, look for silently dropped bodies, check every "equal" metric against the raw numbers, and compare the look against the rulings (for example "no Voronoi flake chips" and "never clip at the tile edge"). Its findings and their evidence go in the commit that resolves them. A phase does not exit with an open finding of "wrong fact" severity.

Words used on this page

critical path The chain of phases where any delay delays the end date.
spike A short, time-boxed experiment that answers one risk question.
go / no-go The decision at the end of a spike: proceed as planned, or take the fallback.
walking skeleton The thinnest version that runs every layer end to end: document → plan → build → STL → audit.
vertical slice One feature carried through every layer before the next feature is started.
parity harness The tooling that builds the same seeds in Python and Rust and compares metrics and renders.
contact sheet One image of many renders side by side: Python beside Rust, four seeds.
golden summary (insta) A stored snapshot of a tile's numbers. A test fails when they change, until someone accepts the change.
stage hash A hash of each stack entry's plan and solids, used to prove a refactor changed nothing.
watertight A closed mesh with no holes or open edges, which the slicer needs.
see-through hole A gap a ray can pass through between stones, which reads as a hole in the print.
overhang red The policy that every render paints faces steeper than the overhang limit red.
twin The KDL document that replaces a .tile.py spec.
freeze Naming a lab commit as the reference for a port. Later lab changes are a new port.
stream A sequence of work that one lead agent carries, beside the others.
S / M / L Size: up to 2 weeks, up to 4 weeks, more than 4 weeks.
