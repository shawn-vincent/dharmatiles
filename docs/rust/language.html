The tile language

A tile is a short KDL text file that names built-in looks (ground, dirt, grass, rock, tree, wall, cliff) and says where they go. Authors write millimetres for a 35 mm square, name tile edges instead of walking lines, describe character in words, and list things in any order. This page is the language as decided, checked against the parser that reads it. The parser (dt-doc) and the first library tiles were built in Phase 1; vocabulary for looks not yet ported can still change in their phase.

1. What a tile document is

A tile document is one .kdl file holding exactly one tile node. The tile has a name, a size and a seed, and a body with:

  • about: optional free text, one string;
  • levels: optional named heights this tile adds or overrides;
  • line and region: only for tiles divided into areas;
  • stack: exactly one, listing the looks and definitions that make the tile.

Above the tile, a file may have use lines that bring in definitions from parts files. Parts files hold define nodes and may hold file-level levels. Two library files use two more top-level nodes: printer (the printer profile) and edges (the edge contract). Anything else at the top level is an error (crates/dt-doc/src/decode/mod.rs:280).

The smallest tile in the library is the Phase 1 walking-skeleton tile:

// library/tiles/test/flat-1x1.kdl
tile flat size="1x1" {
    stack {
        ground                          // flat, at the ground level (5 mm)
    }
}

It names no base. dharmatiles build lib:tiles/test/flat-1x1.kdl builds it for DungeonBlocks, the default system, and adds that base.

look
A built-in generator for one kind of thing or surface: ground, dirt, grass, rock, stone, boulder, pebble, tree, wall, cliff, plus scatter.
control
A setting of a look, written as a property (height=40) or as a child line (height 40).
group
A control that holds only sub-controls, written as properties on its own line: leaf length=4.5 width=3.
thing
One solid object: a rock, a tree, or a definition whose stack is one thing (an oak).
definition
A named, reusable stack (define lawn { … }) that a tile calls like a look.
twin
The KDL tile that replaces a Python .tile.py spec.

2. Syntax basics

Documents are KDL v2, parsed with the kdl crate (6.7.1, KDL v1 features off) and then decoded by hand into a typed model, one function per node type, so every error message is written for the author (crates/dt-doc/src/decode/mod.rs:1).

RuleExampleNotes
A node is a name, then values and properties, then an optional block.tree height=40 { … }Properties are key=value; a block is { … }.
A control may go on the line or as a child line.cliff height=35 or cliff { height 35 }Both decode the same. Edits keep whichever form is written; new controls go on the line (Q2).
Ranges, percents and points are quoted.size="1..6", cover="85%", at="0.65,1"KDL numbers can't contain .., % or ,. A forgotten quote gets an error that says what to write.
Switches are #true and #false.—Bare true is KDL v1 and an error. Few controls are switches: most take a word (top dirt, leaves bare).
// comments a line; /- switches off the next node./- tree
""" opens a multi-line string.about """ … """
Several nodes on one line are separated by ;.region verge { bounded-by trail; fill "0.15,1" }

Values inside quotes

A quoted value is a tiny expression (crates/dt-doc/src/expr.rs:1):

value  := sum ( ".." sum )?        a range "lo..hi", drawn afresh per thing
sum    := prod ( ("+" | "-") prod )*
prod   := unary ( ("*" | "/") unary )*
unary  := "-" unary | atom
atom   := number "%"? | name | "(" sum ")"

A name is a parameter of the enclosing definition or, where a level is expected, a named level: level="ground - 1", level="wall-top / 2". There are no calls, loops or assignments. % is the only suffix.

What every stack entry takes

  • seed=: pins this entry's look while the tile seed changes everything else (crates/dt-doc/src/decode/entry.rs:323).
  • id=: a name for the entry, for edits and diagnostics (entry.rs:338).
  • weight=: only on a child of a scatter, its share of the mix (entry.rs:352).
  • The place words its look accepts (section 5).

3. Units, levels and scaling

The rule for an author is one sentence: write sizes in millimetres for a 35 mm square; other systems scale them for you.

No unit is ever written. Each control knows what it measures (crates/dt-doc/src/schema.rs:23):

Kind of valueWritten asOn another system
Sizemm at the DungeonBlocks reference: thickness 7Scales like a photocopy
Levela named level, mm above the tile base, or an expression: level=foot, level="ground - 1"Scales like a photocopy
Positionsquares from the south-west corner: at="0.65,1"Follows the square
Densityper square: per-square=45Follows the square
Angledegrees: curl="36..81"Unchanged
Sharepercent, quoted: cover="85%"Unchanged
Count, word, switchcount=5, rock mixed, #trueUnchanged

Two optional annotations exist. (mm)4.5 is only a check. (h)1.2 writes a height in wall tops, where h is the 33.1 mm official wall top (schema.rs:19); h is otherwise the engine's internal vertical scale and authors never need it. "4.5mm" is an error.

What scales

Every size the author writes scales with the system. At OpenLOCK's 25.4 mm square a 7 mm wall prints 5.08 mm thick and a 4.5 mm leaf 3.27 mm long. The hidden printability floors never shrink: they come from the printer profile, library/printers/default.kdl:

printer default {
    line     0.45       // one extruded line, mm: the thinnest wall that prints
    layer    0.2        // one layer, mm
    overhang 55         // the steepest overhang that prints, degrees from vertical
    gap      0.2        // the narrowest gap that stays open, mm
}

Looks apply these after scaling, so a scaled blade, leaf or branch is never thinner than what prints (schema.rs:52).

level and height

level is where a surface sits. height is how tall a thing stands above what it stands on: mm (cliff height=35), a word (wall … height full, up to the wall-top level), or a share of the thing it belongs to (ledges 1 height="40%").

The standard levels are a prelude every file sees without a use line. They are compiled into dt-doc from library/parts/levels.kdl (crates/dt-doc/src/known.rs:16):

levels {
    edge     3.4      // ground meets the tile edge here
    ground   5        // today's grass and soil regions
    water    2.6      // shorelab's water level
    wall-top 33.1     // the official wall top
}

A tile adds its own with levels foot=4. The engine keeps each level as a fraction of h, so a build at another scale moves them with everything else.

The edge contract

Every tile also gets library/parts/edges.kdl at its root, without a use line. It says what every tile does at its edges so that neighbours butt with no step:

edges {
    ground level=edge           // ground meets every tile edge at the edge level (3.4 mm)
}

Phase 1 holds the ground's edge level; P2 confirms it against dirtlab and P3 adds the water's edge profile.

4. Edges, points, lines and regions

Positions are in squares from the south-west corner, x running east and y running north (crates/dt-doc/src/place.rs:1).

ThingWritten asMeans
Tile sizesize="2x1"Columns first. Default "1x1".
Edgenorth, south, east, westAs a point: the middle of that edge.
Edge pathalong="north west"Several edges in order, quoted. Two edges meeting make a corner.
Cornernorth-west, south-east, …A point at that corner.
Point"0.65,1"One quoted pair. Either coordinate may be a range: "0.6..1.4,0.6..1.4", drawn once from the tile seed.

A wall or cliff on a tile edge always stands inside the tile, its outer face flush with the edge. That is the DungeonBlocks slab standard, and it means an author never has to work out which side of a line a wall is on.

Lines

A drawn line runs through points (crates/dt-doc/src/decode/mod.rs:784). With a width it is a strip, and a look along= it covers the strip. wobble lets it wander up to that many mm off its points.

line trail width=9 wobble=3 { through south "0.65,1" north }

A look along a drawn line takes side=left, right or centre (the default), as you walk the line. side= along a tile edge is an error, because on an edge a wall always stands inside.

Regions

The whole tile is the default area, so an undivided tile needs no region. A region exists only when lines divide the tile. It is the paint-bucket model from the design conversation: name the lines that bound it, then drop one or more fill points (decode/mod.rs:898, :933).

region verge { bounded-by trail; fill "0.15,1"; fill "0.85,1" }

Several fill points on different sides of a line join areas without union, intersection or difference. Looks act inside a region with in=verge.

5. Placement and scatter

Place words

Four place words, one meaning each, shared by every look (crates/dt-doc/src/schema.rs:180):

WordTakesMeans
in=a region nameActs only inside that region. Default: the whole tile.
along=a line, an edge or an edge pathBuilt along it. On a tile edge, always inside.
at=a point, ranges allowed, or a corner or edge wordCentred there, or drawn once within the range. No at=: anywhere in the area.
against=cliff, wall, rock or treeGathers at the foot of that kind of thing.

Which look takes which word: surfaces (ground, dirt, grass) take in= and along=; things take in= and at=; runs (wall, cliff) take in=, along= and side=, and must have along=; scatter takes in=, along=, against= and at= (crates/dt-doc/src/looks.rs:581).

One thing

A thing is one of itself. How many is never its own control: tree count=3 is an error whose help says to use a scatter. With no at= a thing goes anywhere in its area. Either way its footprint is kept inside the tile and clear of other solids, nudged inward rather than clipped (D12).

scatter

More than one of a thing is a scatter. It says how many and where; its children say what (looks.rs:535).

ControlTakesWhat you get
countnumberHow many, in total.
per-squarenumberHow many per square of the area, or per square of length along a line.
at + spreadpoint; mmA cluster round that point, within this distance.
reachmmWith against=: how far out from the foot.
clumpsper squareGathers them into clumps. Default: spread evenly.
gapmmLeast space between neighbours.
mostlysmall / even / largeSkews every child's size range.
child weight=numberShare of the mix when there are several children. Default: equal.

A scatter must have exactly one of count and per-square; spread needs at=, and reach needs against= (crates/dt-doc/src/decode/entry.rs:958). A scatter inside a surface (dirt { scatter … }) lands on that surface. Hidden inside: Poisson and Voronoi grouping, jitter, group direction.

mostly=

mostly= skews a range draw as lo + (hi − lo) × uk: small is k = 2 (rockpile's skew toward the low end), even is k = 1, large is k = ½ (looks.rs:78).

Stack order

Order is free for solids. Every solid (rocks, trees, walls, cliffs, boulders, scattered or not) is planned before anything grows, and grass and dirt banks grow round every solid wherever they are listed. Order only decides which surface paints over which: a path's dirt listed after the whole-tile dirt paints over it. Each look has a role (surface, thing, run or scatter) that tells the evaluator how to plan it (schema.rs:223).

6. Looks and their vocabulary

Each look leads with a few controls named for what you see. Sizes are mm at the reference scale. A word in a choice expands to the generator's numbers, which are documented next to the word in crates/dt-doc/src/looks.rs; a number is always accepted instead. Words marked provisional below have numbers chosen for the table, which that look's phase (P2–P7) tunes against its lab; the words themselves are decided. These tables are the single source for the planned dharmatiles looks <name> command, the MCP describe_look tool and the JSON Schema (schema.rs:8).

Water and reeds are not in the table yet. They join in their phases (P3, P4). Floors joined in P5.

7. Parts: use, define, param

Parts files hold definitions that tiles bring in by name. A use line names the file and the definitions it brings in, so a reader knows where every name came from:

use "parts/grass" lawn long-grass

A bare path such as "parts/grass" is the bundled library, and "lib:parts/grass" says so explicitly. "./mine" or "../shared/x" is a file in the author's project. Anything else is an error (crates/dt-doc/src/decode/mod.rs:352).

A define has param lines and one stack. It is called like a look; its params are set as properties, and place words (in=, at=) pass through to the looks inside it. A definition can call another. A definition whose stack is one thing is itself a thing, so it can be placed with at= or scattered: scatter count=2 { oak }. Definitions that call each other in a loop are an error (dt::loop).

// library/parts/grass.kdl
define lawn {
    param length 10           // blade length, mm
    param curl "36..81"       // how far a blade bends over, degrees
    param tufts 3             // tufts per square
    param cover "100%"        // share of the ground grassed over

    stack {
        grass length=length curl=curl tufts=tufts cover=cover
    }
}

// Long, curly blades: the species of 2x2-grass-tree.
define long-grass {
    stack {
        lawn length="8..14" curl="63..117"
    }
}

A param's default is typed by the control it fills, so param length 10 is checked as a size in mm. A param without a default must be given by the caller. A tile has no params. Expert controls live in parts files:

// library/parts/trees.kdl (values illustrative, not tuned)
define oak {
    param height 50           // ground to the top of the crown, mm

    stack {
        tree height=height {
            trunk height=18
            crown width=44 clumps=60 shape=wide
            branch split=34 eagerness=0.6 target=0.25 balance=0.8 exponent=3 min-radius=0.9
        }
    }
}

A tile places one oak as oak at="1,1" height=60, or several as scatter count=2 { oak }.

8. Errors and diagnostics

Every problem is a DocError with a stable code (such as dt::unknown-control), a headline, the source span it points at, a label and a hint, rendered by miette (crates/dt-doc/src/error.rs:10). Decoding goes on past a mistake, so all of a file's mistakes come together. Hints come from three places: a did-you-mean over the valid names (schema.rs:311), the table of renamed words from the spike vocabulary (looks.rs:686), and per-rule help text. Examples, from the snapshot tests in crates/dt-doc/tests/snapshots/:

Edits

The GUI and agents change a file through crates/dt-doc/src/edit.rs, which changes only the text it must: set_value (:140) replaces a written value in its written form, insert_property (:169) and set_control (:193) add a control on the line as a property, and remove_control (:230) takes one out. Comments and layout survive.

9. Decisions D1–D12

Two rounds, both on 1 Nov 2026. Shawn first answered the eight syntax questions R6 raised (Q1–Q8). After reading the draft tiles and an adversarial author review, he found the parameters unintuitive and took all ten of the review's recommendations (D1–D10). Then, asked what per-square on a tree was for, he made scatter its own node (D11) and let a thing's position be a range (D12). The plan numbers the same decisions R6.1–R6.8 and V1–V10; both numbers are given.

#DecisionWhy
D1
R6.1		Authors write mm at the DungeonBlocks reference plus named levels. h (the 33.1 mm wall top) stays the engine's scale; (h) is opt-in.The review found h-decimals (foot=0.121 for 4 mm) that no author could compute; the spike's own error message had to do the division. Revises Q1 (authors write h), which came from Shawn's “I think we should do everything with virtual fractions.”

10. Worked examples

All three library tiles are twins of a Python tile or a lab form. Each decodes with the current dt-doc; the library tests read them.

A grass meadow with one tree

// library/tiles/ground/2x2-grass-tree.kdl
// A 2×2 grass meadow with one tree.
// Twin of src/tiles/ground/2x2-grass-tree.tile.py.

use "parts/grass" long-grass

tile grass-tree size="2x2" seed=84 {
    stack {
        ground                          // flat, at the ground level (5 mm)
        long-grass                      // grows round the trunk, wherever it is listed

        tree height=40 {               // anywhere on the tile; or at="1,1"
            trunk height=30             // bare trunk below the crown
            crown width=30 clumps=32 shape=round branching=normal
            leaf length=4.5 width=3
        }
    }
}
  • No region: the whole tile is the default area.
  • The tree has no at=, so it goes anywhere on the tile, as random as the Python tile. at="0.6..1.4,0.6..1.4" would keep it near the middle.
  • The grass is listed before the tree and still grows round the trunk, because solids are planned first.
  • long-grass grows standing blades. The Python tile has only a flat grass carpet, so this is a look change for P4 to confirm.

A fieldstone wall turning a corner

// library/tiles/walls/1x1-wall-fieldstone-corner.kdl
use "parts/grass" lawn

tile wall-fieldstone-corner size="1x1" seed=64 {
    stack {
        dirt                                // bare earth at the ground level

        // Along the north edge, then the west edge.  On a tile edge a
        // wall always stands inside, its outer face flush with the edge.
        wall along="north west" style=fieldstone seed=14 {
            height full                     // up to the wall-top level (33.1 mm)
            thickness 7
            coping loose                    // or: on-edge

            // fieldstone's own defaults, written out to show them
            stones height="2.2..5.2" length="5..16"
            joints width=0 depth=2.8        // how deep the gaps between stones look
            edges rounding="1.3..2.6"       // worn corners
        }

        lawn
    }
}
  • Two edges in along= make a corner.
  • The wall's seed=14 pins its stones while the tile seed varies everything else.
  • On OpenLOCK, the 7 mm thickness and the stone sizes all shrink with the square.

A cliff run

// library/tiles/cliffs/2x1-cliff-run.kdl
// Twin of clifflab/rockpile.py's `run` form (round 15, commit 3b56ae0).

tile cliff-run size="2x1" seed=1 {
    about """
        Rock band against the north edge. Both ends finish in the
        standard end section, so runs butt end to end.
        """

    levels foot=4                   // rockpile's foot; the standard edge level is 3.4

    stack {
        dirt level=foot {
            bank against=cliff height="1.5..3.5" reach="3..6.5"
            scatter per-square=45 { pebble size="1..2.2" buried="20%..50%" }
        }

        cliff along=north height=35 {   // 35 mm above its foot
            rock mixed                  // or: columns, blocks, slabs
            stone-size massive          // or: rubble, broken
            top dirt                    // or: bare
            shattered patches=3 width="5..10"
        }

        // scree: fallen stones gathered at the cliff's foot
        scatter against=cliff per-square=55 reach=4 { stone size="1..6" mostly=small }
        scatter against=cliff per-square=2.5 { boulder size="4.5..8" }
    }
}
  • levels foot=4 adds a level for this tile. It goes when rockpile moves to the 3.4 mm edge level (Q6).
  • The dirt is listed before the cliff and still banks against=cliff. Its pebbles are scattered on the dirt.
  • Scree is stones and boulders scattered against the cliff; they take their fragment shapes from the cliff's rock.

A divided tile: grass, a path and a rock cluster

This tile was written from scratch to test the language on something the Python tiles could not say. It lives as a test fixture, crates/dt-doc/tests/fixtures/1x2-grass-path-rocks.kdl, not in the library.

use "parts/grass" lawn

tile grass-path-rocks size="1x2" seed=7 {

    // From the middle of the south edge to the middle of the north edge,
    // 9 mm wide, wandering up to 3 mm off its points.
    line trail width=9 wobble=3 { through south "0.65,1" north }

    // Everything beside the path: one fill point on each side of it.
    region verge { bounded-by trail; fill "0.15,1"; fill "0.85,1" }

    stack {
        dirt                                    // the whole tile, at the ground level
        dirt along=trail level="ground - 1"     // the path, trodden 1 mm lower

        scatter in=verge at="0.2,1.4" spread=6 count=5 {   // a cluster
            rock size="4..10" shape=rounded buried="30%"   // shape: or angular, flat
        }

        lawn in=verge cover="85%"
    }
}
  • The second dirt paints over the first along the path, 1 mm lower: here order matters, because both are surfaces.
  • verge is the tile less the path: one fill point on each side of the line.

11. Differences from the R6 page

The R6 spike page (now in spikes) described the vocabulary before dt-doc was reworked. The as-built language, described above, differs in these ways:

  • Two more top-level nodes: printer (library/printers/default.kdl, the printability floors) and edges (library/parts/edges.kdl, the edge contract, applied to every tile without a use line).
  • use paths: a bare path is the bundled library; lib: is optional; ./ and ../ are project files. The review's examples wrote lib: always.
  • Every stack entry takes id=, besides seed=.
  • Defaults the R6 page did not state are now fixed in the table: crown clumps 200, rock size "2..10", wall style cut-stone, cliff stone-size rubble and top bare, grass flow wavy, dirt clods some.
  • Many word values have provisional numbers (crown cone/wide/tall, branching open/dense, rock columns/blocks/slabs, stone-size broken, clods few/many, flow combed/wild, wall height low), to be tuned in each look's phase.
  • The "1..6^2" skew is gone entirely, with an error pointing at mostly=. The review had proposed keeping it as an expert form.
  • The cliff's rock takes explicit weights as sub-controls: rock columns=… blocks=… slabs=… odd=… monoliths=….
  • Water, reeds and floors are not in the look table yet (P3–P5).
  • The 1×2 path tile is a test fixture, not a library tile; the library adds tiles/test/flat-1x1.kdl.
  • The edit API inserts properties (insert_property, set_control) and removes controls; the R6 page said it could only replace values.

History

The language came out of a long design conversation with Shawn, archived as input-language-design-conversation.md. From it: files editable by hand, by agents and in a GUI; regions as lines plus fill points; standard heights; definitions that are “sometimes tiles and sometimes other things (like rocks or trees or grass surfaces)”. An early YAML-like sketch gave way to KDL v2 before Phase 0. Phase 0 spike R6 then tested the parser, round-trip printing and edits on three twins of Python tiles; its results are on the spikes page. The h-based heights of that spike were replaced by millimetres on 1 Nov 2026 (D1), and dt-doc was reworked to this vocabulary as Phase 1 stream A (commit 6fb2205 on rust/p1-doc). For where the language sits in the engine, see architecture; for the phases, the plan.
