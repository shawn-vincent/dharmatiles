Where everything goes

A file layout for the Rust version that a Rust developer would recognise on sight: one Cargo workspace at the repo root, six crates, one command-line program, and the tile library as plain KDL files that ship inside the program. Each choice below is ranked as standard, common or progressive, and each crate boundary has to earn its place.

New in revision 3. This page replaces the fifteen crates sketched on the architecture page with six, and adds the parts revision 2 left open: binaries, installs, GUI, mobile, MCP, data folders, user paths and how the Rust code sits beside the Python during the port. Every edit to other pages is in the change log.

The short version

dharmatiles/
├─ Cargo.toml          workspace: members, shared versions, lints
├─ rust-toolchain.toml exact Rust version
├─ dharmatiles.kdl     project file for the bundled library
├─ crates/
│  ├─ dt-geom/         grid · 2D · mesh · rays · seeds
│  ├─ dt-kit/          scene + ~20 ops + audit + export
│  ├─ dt-doc/          KDL → typed model (no geometry)
│  ├─ dt-looks/        hills … connector
│  ├─ dt-eval/         plan → build, cache, build API
│  └─ dharmatiles/     the one binary
├─ app/                Tauri GUI (later)
├─ library/            tiles · parts · printers · palettes
├─ xtask/              repo chores in Rust
├─ docs/
└─ out/                build output, git-ignored
  1. One repo, Rust at the root. The Python stays exactly where it is until each look is ported; Cargo ignores folders that aren't members.
  2. Six crates, not fifteen. Four boundaries pay for themselves: the document model builds without geometry; looks can only use the kit's public operations; the geometry kernels hold every native dependency; and evaluation is shared by every front end.
  3. One program, dharmatiles, with subcommands: build, check, watch, preview, mcp and a few more. The GUI is a separate Tauri app that links the same crates.
  4. One web front end, three hosts. The Tauri desktop app, Tauri on phones, and dharmatiles preview in any browser all show the same three.js viewport.
  5. The tile library ships inside the program and is addressed as lib:. Your own tiles live in a folder you can see (~/Documents/dharmatiles). Output goes to out/ beside the project, as the labs already do.

Words used on this page

crate
Rust's unit of compilation and of dependency. A crate is a library or a program, with its own Cargo.toml.
workspace
Several crates in one repository that share one lock file, one build folder and shared settings. A virtual manifest is a root Cargo.toml that lists the crates but is not a crate itself.
feature
A named on/off switch in Cargo.toml that adds code or dependencies, for example choosing which Manifold backend to compile.
wasm
WebAssembly: Rust compiled to run inside a web browser. wasm32-unknown-unknown is the plain browser target; wasm32-unknown-emscripten is the target that can also carry C++ code.
FFI
Calling C or C++ code from Rust. Manifold is C++, so manifold-csg uses FFI and needs a C++ compiler at build time.
MCP
Model Context Protocol: the standard way an AI agent calls a program's tools. Runs over stdin/stdout (stdio) or HTTP.
LSP
Language Server Protocol: how editors get errors, completion and hover help for a file format.
MSRV
Minimum supported Rust version, declared as rust-version.
xtask
A small Rust program in the repo, run as cargo xtask …, that replaces shell scripts and Makefiles for chores.
rank
standard what Cargo documents or most Rust projects do · common widely used, with a track record · progressive newer, forward-leaning, fewer users. pick marks the recommendation.

Considered and rejected: one crate with modules (simplest, but the document model would then need Manifold to compile, and every edit rebuilds everything); a crate per kernel (four crates that always change together); separate mcp and lsp crates (they only call dt-eval and dt-doc).

4 GUI and live preview

The language conversation settled this: one codebase everywhere because you won't test on every platform (L30), "a web view is probably fine" (L106), and ChatGPT's ranking for October 2026 was Tauri 2, then Dioxus, then Slint (L53). The GUI it sketched is mostly 2D (draw lines, paint-bucket regions, an inspector) beside a live 3D preview (L1128).

Live preview, one mechanism. The notify crate watches files. dt-eval rebuilds only the stack entries whose inputs changed (cache by path, seed and input hash). It pushes the plan pass first (regions, footprints, heights in under a second), then each entry's mesh as a binary buffer of positions and material ids. The Tauri app receives these as events and the browser preview over a websocket; the viewer code is the same. The front end starts as plain ES modules with a pinned copy of three.js and no bundler; add Vite and TypeScript only when the UI grows.

6 MCP server

The official Rust SDK is rmcp (3.x in 2026; 3.0.1 and 3.1.0 on docs.rs). It targets the 2026-07-28 MCP spec, with stdio and Streamable HTTP transports; HTTP is stateless in that spec version. A separate community SDK, rust-mcp-sdk 2.0, exists; don't confuse the two.

Tool inputs use the same JSON Schema that dt-doc derives for the GUI, so there is one contract. render_preview needs an offscreen renderer. A small CPU rasteriser in dt-kit (depth buffer, simple shading, red paint) is about 300 lines, deterministic and wasm-safe, and the same code gives build --png and the side-by-side contact sheets for render review. The MCP module lives in crates/dharmatiles/src/mcp.rs, behind a default-on feature.

Where does it go?

Questions only Shawn can answer

1. Rust at the repo root, beside the Python?

The recommendation is yes, with the Python untouched until each look is ported. The alternative is a rust/ folder or a new repo.

2. Will anything be published to crates.io?

If not, crates keep the short dt- names and installs come from GitHub releases, Homebrew or cargo install --git. If yes, every library crate needs a unique name such as dharmatiles-geom.

3. Licence?

Code under MIT OR Apache-2.0 is the Rust default. The tile library and reference renders could use a content licence (for example CC BY) or stay all rights reserved. This also decides whether Slint's GPL option would ever matter.

4. Is out/ the right name to replace stl/?

The labs already use out/, and 3MF output makes stl/ misleading. Inside it: out/db/… and out/ol/…, as today.

5. Your own tiles in ~/Documents/dharmatiles?

Visible and easy to back up, like OpenSCAD's libraries folder. The alternative is a hidden app-data folder.

6. Config in ~/.config on the Mac?

Most CLI tools you'd hand-edit config for (gh, helix, starship) use ~/.config on macOS. A Mac-native app would use ~/Library/Application Support. One app with both a CLI and a GUI has to pick one.

7. Is lib: a good name for the bundled library?

Alternatives: std:, @dharmatiles/. The point is that it is explicit, so nothing is resolved by search order.

8. What should phones do first?

View and edit while builds run on a desktop, or build on the phone too? The second depends on the pure-Rust Manifold proving out.

9. Is the program name dharmatiles too long to type?

A short alias such as dtiles could ship as well. One name is simpler.
