From spikes to cutover

A phased plan for the Rust rewrite, built mostly by Claude agents and directed by Shawn. Nine phases, three work streams, and about 32 weeks on the critical path (25 to 40 is the honest range). Every phase ends with something Shawn can print, and no look counts as ported until he judges its renders equal to the lab's, side by side, over four seeds.

Starting point. Shawn accepted the revision 3 recommendations ("i like the recommendations"). Where a page still lists an open question, this plan uses the recommended default and marks it assumed. The list is under Assumed defaults, and nothing in the plan waits on them.

What changed from the feasibility page's migration order. Four refinements, each with its reason under Why the order changed. The skeleton gets its own phase, together with the parity harness, ahead of dirt. Walls, floors, OpenLOCK and trees run as a second stream beside grass. The library cutover comes before the cliff, because no library tile uses the cliff. The front ends arrive across the phases instead of all at the end.

How the phases depend on each other

The critical path

P0 (3) → P1 (3.5) → P2 (3) → P3 (6) → P4 (7) → P6 (1.5) → P7 (8) ≈ 32 weeks, finishing around mid-June 2027. If every phase lands at the short end of its range, that is 25 weeks; at the long end, 40. P5 has about four weeks of slack beside P4. The front-end stream is small and never on the path.

The real constraint is Shawn's review time, not agent throughput. Each look needs one or two rounds of side-by-side review, and some need a test print. So the plan never runs more than two look streams at once. If the review queue grows past two weeks, stream B pauses (see kill and pivot).

The faster schedule. If rockpile is frozen by about week 18, the cliff can start in stream B as soon as P5 ends. Then P7 no longer follows the cutover, and the total drops to about 26 weeks. Use the toggle above the timeline to see it.

Workspace skeleton, CI, toolchain and lints

  • Manifest: a virtual manifest with members = ["crates/*", "xtask"] (app/src-tauri is added in P8), resolver = "3" and edition 2024. One version, edition, licence and rust-version sit in [workspace.package], and every external version is stated once in [workspace.dependencies]. Dependencies get opt-level = 3 in dev builds.
  • Toolchain: rust-toolchain.toml pins the exact current stable, with rustfmt, clippy and the wasm32-unknown-unknown target. Bump it on purpose, with the golden hashes as the check.
  • Lints: in [workspace.lints], unsafe_code = "forbid" (FFI lives inside the binding crates, not ours), plus a short Clippy list (dbg_macro, todo, unwrap_used outside tests, float_cmp, cast_possible_truncation as warnings). There is no rustfmt.toml. Every crate opts in with lints.workspace = true.
  • CI: on every push, fmt --check, clippy -D warnings, and tests on macOS arm64, Linux x86 and Windows. Also cargo check -p dt-geom --target wasm32-unknown-unknown --no-default-features --features manifold-rust (moved to dt-eval in P1), and cargo deny for licences, advisories and duplicate versions.

The KDL parsing approach

Use the kdl crate (KDL v2, format-preserving; confirm the current version at start) to parse into a node tree. Then decode by hand in dt-doc, with about one function per node type (tile, define, line, region, stack, and each look). Keep source spans so miette can point at the mistake. There is no derive crate: knus needs co-maintainers and facet-kdl is young. Values go through one small hand-written expression parser covering arithmetic on parameters, distributions ("a..b^k"), named heights and field constructors. It has no loops, assignments or call chains. JSON Schema comes from the typed model through schemars, printed by dharmatiles schema and never committed.

The parity harness

It is built in P1, before any look is ported, and every look phase uses it. The harness never compares meshes byte for byte, because Python and Rust can't match that way (different RNGs, EDT tie-breaks and kd-tree order). It compares what Shawn judges: numbers that describe the look, and painted renders side by side.

  • Same seeds: 1, 2, 3 and 4 for every look. These are lab seeds. Rust's path-derived seeds won't reproduce Python's random streams, so a seed means "the same test case", not "the same random tile".
  • Metrics: one set per look, computed by the same code from either STL: bare fraction, blade count and height range, rock count and size histogram, facet count, relief spectrum, wave amplitude, overhang mm², see-through holes, dropped bodies and time. Tolerance: within ±10% or within Python's own spread across the four seeds, whichever is wider.
  • Golden summaries (insta) per tile: stage hashes, triangle count, volume, overhang mm² and holes. cargo insta review shows what changed. STLs are never committed.
  • dt-py is not needed for this. The harness compares files, so it works with the labs exactly as they are. dt-py is built only if a kernel test needs Rust and Python on the same arrays assumed.

Output, the Python library and the labs

Ongoing practices

Definition of done, per look

  1. Every library tile that uses the look has an approved KDL twin, and its .tile.py is deleted.
  2. The metrics are within tolerance over seeds 1 to 4.
  3. The printability gate passes: watertight after float32 reload, 0 see-through holes, overhang at or below budget and painted red in every render, and nothing dropped silently by keep-largest.
  4. Shawn signs off the Python-beside-Rust contact sheet as equal or better. This is the bar. Numbers alone never close a look.
  5. The look builds within its time budget, and its stage hashes are stable at 1, 4 and 16 threads.
  6. The look's controls show in dharmatiles looks <name> with units, ranges and defaults. Internal constants stay internal.
  7. The OpenLOCK build has been checked, from P5 on.
  8. A test print has passed where printability is at stake: water edges, grass tips, walls, trees and cliffs.
  9. A simplify review is done and a change log entry is written.

Simplify and DRY reviews

Shawn's habit is to stop periodically and ask whether the system is growing more complex. The plan makes that a fixed cadence: every two weeks, and at every phase exit, a fresh agent with Orin's brief reviews the diff, with no knowledge of the plan's reasoning. It reports a complexity ledger against budgets:

MeasureBudgetIf over
Kit operations in dt-kit's public APIabout 22Every new op needs a written reason and must be used by at least two looks, or be merged.
Look-private mechanisms (noise, sampler, fade, mesher, rounding)0Move it into the kit or delete it. This is how the 70 duplicates happened.
Public controls per look≤ 10 (cliff ≤ 12)Move the extras to fixed internals or presets.
Document ideas6A seventh idea needs Shawn's ruling.
Crates6 (+ later 3)A new crate needs a boundary that pays, as on the layout page.
Lines per look in dt-lookstrend onlyFlag any look that grows more than 20% in a phase without a new control.

Adversarial reviews

Each phase exit gets one adversarial review by a fresh agent that has the code, the exit criteria and Shawn's rulings, but not the implementers' conclusions. It tries to break the claims: rerun the determinism checks, feed malformed documents, look for silently dropped bodies, check every "equal" metric against the raw numbers, and compare the look against the rulings (for example "no Voronoi flake chips" and "never clip at the tile edge"). Its findings go into the change log as entries with evidence, as revision 2's did. A phase does not exit with an open finding of "wrong fact" severity.

The change log

The analysis and plan keep their change log in changelog.html, with one revision section per change of plan, and each entry giving before, now and why. All Claude-written documents are HTML under docs/, generated and never edited by hand. For the code, a release log is generated from commit messages at P6 assumed, which replaces the layout page's hand-written root CHANGELOG.md to follow the HTML-only rule.

Words used on this page

critical path The chain of phases where any delay delays the end date.
spike A short, time-boxed experiment that answers one risk question.
go / no-go The decision at the end of a spike: proceed as planned, or take the fallback.
walking skeleton The thinnest version that runs every layer end to end: document → plan → build → STL → audit.
vertical slice One feature carried through every layer before the next feature is started.
parity harness The tooling that builds the same seeds in Python and Rust and compares metrics and renders.
contact sheet One image of many renders side by side: Python beside Rust, four seeds.
golden summary (insta) A stored snapshot of a tile's numbers. A test fails when they change, until someone accepts the change.
stage hash A hash of each stack entry's plan and solids, used to prove a refactor changed nothing.
watertight A closed mesh with no holes or open edges, which the slicer needs.
see-through hole A gap a ray can pass through between stones, which reads as a hole in the print.
overhang red The policy that every render paints faces steeper than the overhang limit red.
twin The KDL document that replaces a .tile.py spec.
freeze Naming a lab commit as the reference for a port. Later lab changes are a new port.
stream A sequence of work that one lead agent carries, beside the others.
S / M / L Size: up to 2 weeks, up to 4 weeks, more than 4 weeks.
