Booleans, materials and determinism

manifold-csg replays every boolean from the cliff and tree tiles watertight, with Python's triangle counts and volumes, at Python's speed. Source IDs survive a union and a level set. The test pipeline is byte-identical at 1, 4 and 16 threads, and also identical between macOS-arm64 and Linux-x86_64 for everything except calls into the platform maths library.

R1 gomanifold-csg, parallel on

21,570 results across 3 tiles: all watertight, triangle counts equal to Python on all of them, worst volume error 4.9e-10, time 1.01–1.09× Python on paired runs.

R1 port: not defaultmanifold-rust stays the wasm backend

Every result watertight, carried IDs and properties match, but triangle counts differ from Python on 14 rockpile and 10 massif ops, and it takes 2.0× (rockpile) to about 3× (massif) Python's time with rayon on. Gate was ≤1.5×.

R9 goEvery triangle maps to a source

Union: 36/36 triangles carry one of the two source IDs and lie on that source. Level set + union: 28,016 triangles traced back to their source triangle and its co-sampled material, 0 unmapped. Both backends.

R2 goByte-identical on one machine

Every stage hash equal at 1, 4 and 16 threads, twice each, on both backends, with Manifold's own parallelism on and off. Two needed rules: keyed seeds, and original IDs assigned in index order.

The baseline is a Python replay, not the in-situ time

Two things made the in-situ numbers unusable as the yardstick. First, the three captures ran at the same time, so their timings are inflated. Second, a re-imported operand is not the same object as the in-memory one: replaying the captures in Python itself changes the triangle count on 448 of 4,800 rockpile results and 1,461 of 16,676 massif results. So the comparison is Rust against replay_py.py: the same .dtm inputs, re-imported the same way, timed the same way (the op plus forcing num_tri()). manifold-csg's C API cannot pass face IDs in, so its baseline drops them too.

What R1 turned up

  1. Parallel must be on. With Manifold built without TBB, manifold-csg takes 3.1–3.3× Python's time on rockpile and 3–5× on the massif. With TBB it matches. It is now on by default (manifold-parallel). Sequential and parallel builds also give different triangles on a handful of ops (2 of 4,800; 1 of 16,676), and the parallel build is the one that matches Python.
  2. manifold-csg cannot import face IDs or run transforms. The C API's MeshGL64 options carry runs, merge vectors and tangents only. For the replay this made no difference (counts still match Python given the same inputs), but it means a mesh that leaves Manifold and comes back loses its coplanar-face grouping. Keep solids inside the kernel between ops; do not round-trip through TriMesh.
  3. Original IDs come from a process-wide counter. Plane ops mint a new ID for their half-space, and parts made in parallel get IDs in scheduling order. The replay compares only IDs carried from operands; R2 shows the consequence for determinism.
  4. Original-ID mismatches are all edge cases. 11 of 21,570 results: 8 intersections whose result is a zero-volume sliver on one side and empty on the other (largest 1.2e-4 mm³), and 3 plane trims where one side kept the half-space's minted ID and the other did not. Harmless, but the audit should count zero-volume slivers.
  5. The parity harness must compare metrics, not bytes. Even same-engine, same-input results are byte-identical to Python only 74–92% of the time (version 3.5.3 against 3.5.1 and re-import order). Triangle counts and volumes match.
  6. The port is close but not there. Sequentially it matches the C++ kernel's speed (24.3 s against 22.9 s on rockpile), and its rayon build gave the same whole-run hash as its sequential build on both cliffs, confirming the bit-identical claim. But its parallelism buys 1.7× where TBB buys 3×; its batch_boolean folds left to right (101 s on rockpile until PortSolid::batch was changed to union smallest-first); and it tracks Manifold 3.5.4, so its triangulation differs from Python's 3.5.1 on 24 ops and is byte-identical to it on only about 15% of results.
  7. A toolchain trap on this Mac. rustup here is the x86_64 build running under Rosetta. Through it, the cmake build of Manifold compiled x86_64 objects into an arm64 binary and failed to link. Calling the arm64 toolchain directly (~/.rustup/toolchains/1.99.1-aarch64-apple-darwin/bin first in PATH) fixed it. Reinstalling rustup natively would fix it for good.

R2: determinism

crates/dt-geom/tests/determinism.rs: value-noise fBm on a 384² grid, keyed-seed scatter, an exact EDT (Felzenszwalb, rows and columns in parallel), then 24 level-set rocks trimmed by the ground in parallel and one batch union with the slab. A further hash covers a sin/exp stage to measure the platform maths library. Each stage is hashed at 1, 4 and 16 rayon threads, twice each.

One machine

The first run failed: the final union differed between 1 and 4 threads on both backends while every rock was identical. The cause is Manifold's process-wide original-ID counter. Rocks built in parallel get IDs in scheduling order, and a boolean orders its output triangles by original ID. Re-assigning IDs in index order (as_original()) before the batch fixed it. With that rule, every hash is identical at every thread count, debug and release, with Manifold's parallelism on and off. The R1 replay adds a larger check: two runs of all 4,800 rockpile and all 16,676 massif ops with TBB on gave the same whole-run hash (692c31a3… and f99638b2…).

Commit 89bf704, Manifold parallelism on. The first CI run (parallelism off, the port's left fold) showed the same pattern: identical on macOS and Linux, different on Windows for libm, rocks and union.

Our own code is identical everywhere as long as it avoids libm. Manifold, in both its C++ and Rust forms, is byte-identical between macOS-arm64 and Linux-x86_64 on this pipeline, and differs on Windows with the same triangle counts; the likely source is MSVC's sin/cos in the plane and level-set paths. The C++ kernel and the port never agree byte for byte with each other (different rocks and 32,288 against 32,262 triangles), because the port tracks Manifold 3.5.4 and manifold-csg ships 3.5.3.

Level for Shawn to choose: byte-identical golden hashes are achievable for macOS and Linux together; Windows needs its own hashes or a metrics-plus-render gate. Seeded code paths should use the libm crate rather than std transcendental functions.

What changes in the plan

  1. Ship manifold-csg with Manifold's parallelism on. The design note "run each boolean single-threaded and many in parallel" is not needed for identity on one machine, and costs 3–4× on the cliff's big unions.
  2. Add a kernel rule: assign original IDs in index order before combining parts made in parallel. Without it, output depends on thread scheduling.
  3. Keep solids inside the kernel between ops; a TriMesh round trip through manifold-csg drops face IDs.
  4. The parity harness compares triangle counts, volumes and renders, not bytes, against a Python replay.
  5. R1 ran at a larger scale than planned: single meshes up to 7.1M triangles and a 202-part, 13.2M-triangle union on the massif, not 1.7M. The kill criterion (cliff batch within 2× Python) is met with room to spare.
  6. R2's cross-platform level: macOS and Linux can share golden hashes; Windows cannot without replacing libm calls inside Manifold.
  7. manifold-rust stays behind the trait as the wasm backend (the browser build compiles), and is re-measured when Python moves to Manifold 3.5.4 and the port's parallel speed improves. The R1 replay is the re-test: r1_replay --backend port.
