Three tiles in KDL

The grass-and-tree tile, the fieldstone wall corner and a rockpile cliff run, written as KDL v2 documents and decoded by the new dt-doc crate. The question for your 30 minutes: could you write these? Is anything missing?

How to read them

across
Squares. through 1 1 0 1 0 0 is the north-west corner of a 1×1, with y running north.
up
h, where 1 is the 33.1 mm wall top. Named heights (ground, wall, a tile’s own foot) stand in for numbers.
details
True millimetres: blades, leaves, stones, scree. Angles are degrees. Each control knows its own unit, so none is written.
shape
tile or define, then param, line, region and stack. A stack entry is a look or a definition, with name=value controls and group lines such as leaf length=4.5.
KDL v2
#true/#false; bare words such as form=run; /- switches off the next node; """ opens a multi-line string.
Colours: nodecontrol="string"number#true// comment

2x2-grass-tree

Where the design didn’t fit

  • There is no grass-carpet look. GrassCarpet (embossed 2D stamps) is not one of the twelve looks; meadow replaces both the carpet and the 3D blades. The species values arrive as meadow controls (blade length curl clearance, clumps per-square), but grasslab v3’s meadow has fixed 4-line stroke blades of 3.5–6.5 mm and no curl control today. P4 must add these controls to meadow or decide they go.
  • The grass moves from first to last in the stack, so the blades steer round the trunk. The Python carpet was stamped under the tree.
  • The 5 mm ground height was implicit in Python (the region took its first layer’s height_default_mm). The twin says it: hills height=ground.
  • Blade curl was a fraction of π (0.35–0.65). Documents use real angles, so it is 63–117°.
  • The Python SpeciesConfig object shared between two layers becomes define long-grass in parts/grass.kdl, which itself calls define lawn.
Python it replaces: 2x2-grass-tree.tile.py 
"""2x2 grass meadow with one Tree (space-colonisation growth, Bezier tubes)."""

from dharmatiles.spec import Tile, Region, FloodFill, SurfaceConfig, SpeciesConfig, D
from dharmatiles.layers import GrassCarpet
from dharmatiles.scatter import Tree, Grouped, Uniform

_species = SpeciesConfig(
    blade_length=D[8:14],
    blade_curl=D[0.35:0.65],
    blade_clearance=0.2,
)

tile = Tile(
    surface=SurfaceConfig(cols=2, rows=2, seed=84),
    areas=[
        Region(
            id='meadow',
            selector=FloodFill(0.5, 0.5),
            layers=[
                GrassCarpet(
                    species=_species,
                    placement=Grouped(groups_per_square=3),
                ),
                Tree(
                    placement=Uniform(count_per_square=0.25),
                    debug_attractors=False,
                    foliage_clusters=True,
                    n_attractors=32,
                    leaf_length_mm=4.5,
                    leaf_width_mm=3.0,
                ),
            ],
        ),
    ],
)

1x1-wall-fieldstone-corner

Where the design didn’t fit

  • Which side of the line. Python puts the wall body on the left of the spine as you walk it, silently. The twin keeps that rule and says it in a comment. Left and right were ruled out for regions, not for things built along a line.
  • Python’s two grass layers (carpet before the wall, blades after it) become one lawn after the wall.
  • SoilCarpet becomes dirt (dirtlab), which is a different look; the ruling “exposed ground = dirt everywhere” makes that the intended change.
  • The wall’s own seed=14 fits the design directly: any entry may pin its seed.
  • Thickness 7 mm is written as layout, 0.2 squares, so an OpenLOCK build makes it 5.1 mm. See question 5.
  • The fieldstone defaults (courses, bays, reveal, roundover, coping) are written out to show what the look takes; the Python spec set none of them.
Python it replaces: 1x1-wall-fieldstone-corner.tile.py 
# 1x1-wall-fieldstone-corner.tile.py
#
# Drystone fieldstone wall turning the NW corner of a grassy 1x1.
# Wall body extends to the LEFT of the spine walk (into the tile);
# outer face flush to the tile edge — the DungeonBlocks slab standard.

from dharmatiles.spec import Tile, Region, FloodFill, SurfaceConfig, \
    SpeciesConfig
from dharmatiles.layers import SoilCarpet, GrassCarpet
from dharmatiles.scatter import Grass
from dharmatiles.walls import FieldstoneWall

_species = SpeciesConfig()

tile = Tile(
    surface=SurfaceConfig(seed=64),
    areas=[
        Region(id='meadow', selector=FloodFill(0.5, 0.35), layers=[
            SoilCarpet(),
            GrassCarpet(species=_species),
            FieldstoneWall(spine=[(1.0, 1.0), (0.0, 1.0), (0.0, 0.0)], seed=14),
            Grass(species=_species),
        ]),
    ],
)

2x1-cliff-run

Where the design didn’t fit

  • The architecture sketch didn’t fit. It drew a line foot, a region shelf and cliff self=shelf. Rockpile takes no foot line: a run grows from a tile edge (its “back” plane) out to a generated depth of 8–20 mm with gullies and buttresses. The twin names that edge as a line, cliff along=back, the same rule as walls. A corner is then a two-segment line and a canyon two lines. P7 must either restrict along to tile edges or generalise rockpile’s band forms to any line.
  • Rockpile builds the foot bank, the scree, the dirt on the tops and the cliff in one function, all sharing the shattered zones. The twin splits them into dirt (with a bank), cliff and scree. That works only because builds see every plan: dirt is below the cliff in the stack but banks against the cliff’s planned footprint, and the cliff must publish its zones in its plan.
  • Rockpile’s foot ground is 4.0 mm; the confirmed edge level is 3.4 mm. The tile keeps 4.0 with heights foot=0.121. See question 6.
  • Of rockpile’s 169 constants the twin carries 24 as controls. The form preset fixes the plan (depth, tiers, gullies, buttresses, the 4 mm end section), and stacking, dressing, cracks, relief, grain, seats and the core stay inside the look, as the architecture intends.
  • The lab’s command line builds N×N only; build() takes any cols and rows, and 2×1 is the natural run piece.
  • Forms whose height is a pair (escarpment’s 10–40 mm ramp along the run) are not distributions: "10..40" would mean a random height. A ramp needs its own form. See question 7.

Shared parts

Two files in library/parts/ show the definition and import mechanism. lawn holds Python’s default species; long-grass calls lawn with three overrides, a definition nested in a definition. Tiles bring them in with use "lib:parts/grass".

When a document is wrong

Each case breaks one real tile on purpose. The text is exactly what cargo run -p dt-doc --example errors prints (miette, without colour). Every error points at the text that caused it and says what to write instead.

Questions where the syntax could go either way

  1. What is h in millimetres? The tiles use h = 33.1 mm, the official wall top, so wall is exactly 1 as you described. Everything else then gets awkward decimals: ground 0.151, the cliff 1.057. The architecture sketches used h = 40 mm. Named heights hide most of it.
  2. Scalar controls on the line, or as children? Both work today: cliff … mass=1.35 and, inside its block, mass 1.35. The cliff tile uses children (room for a comment each); the tree uses properties. Keep both, or pick one?
  3. Units: never, annotation, or suffix? The axis supplies the unit, so the tiles write none. A unit can still be written as (mm)4.5 or inside a string, "4.5mm", and a wrong one is an error. Allow one form, both, or forbid units?
  4. Ranges must be quoted. KDL numbers can’t contain .. or %, so it is size="1..6^2" and column="38%". The error for a forgotten quote says so. Acceptable?
  5. Is wall thickness or tree size layout or detail? Layout (squares, h) scales with OpenLOCK’s 25.4 mm square; detail (mm) doesn’t. The twins put wall thickness and tree height in layout units and stones, blades and leaves in mm.
  6. The cliff foot level. Keep rockpile’s 4.0 mm foot as a tile override, or move the cliff onto the 3.4 mm edge level now?
  7. How is a ramp written? For escarpment heights that change along the run: height from=0.3 to=1.2, or a field value, or leave it inside the form preset?
  8. Standard heights: implicit or imported? Every tile sees ground, edge, water and wall without a use line. Or should a tile write use "lib:parts/heights"?

The dt-doc crate

  • Parse with kdl 6.7.1, then decode by hand: one function per node type (tile, define, param, line, region, stack entry, group), with one control table per look in schema.rs. No derive crate.
  • Every name and value keeps its byte span. Errors are miette diagnostics with a code, a label at the span and a help line. Decoding continues past the first error, so a file’s mistakes come together.
  • Values go through a small expression parser: arithmetic on parameters and named heights, ranges "a..b" with an optional skew ^k (a draw is a + (b − a)·u^k, rockpile’s rule), percents. No calls, loops or assignments.
  • Dependencies: kdl and miette only (no default features). It builds for wasm32-unknown-unknown, which CI now checks.
  • Two things learned about KDL v2: two nodes on one line need a ; after a closing brace, and the crate’s own messages are generic (“Expected identifier string”), so dt-doc rewrites the common ones (v1 keywords, unquoted ranges).
