Rays without Embree

Go, with the distance clause relaxed. On the leaf placer's ray batches, obvhs returns the same triangle as Embree on 100% of rays in two of three captures and 99.9995% in the third (2 of 401,793 rays differ). The 1e-4 mm distance clause passes only on the first capture: the two later ones reach 1.45e-4 and 1.79e-4 mm, float32 rounding of about 20 ulps at the tree's size. Builds hash identically at 1, 4 and 16 threads, and a single-threaded query is 2.5–2.8× Embree's time (gate ≤ 3×). Use obvhs 0.4 with Embree's triangle test and medium_build, and keep parry3d behind the same trait as the spare. The embree3 fallback is not needed for the leaf placer.

What was measured

tests/parity/capture/rays.py wraps trimesh's embreex layer (_EmbreeWrap) from outside and records every scene and ray batch exactly as Embree saw them: float32 vertices in trimesh's scaled frame, float32 origins and directions, and Embree's primID and tfar. It captured two builds:

  • Leaf placer: 2x2-grass-tree.tile.py at DungeonBlocks scale, built in memory (no STL written). 1,875 leaves placed; 80 scenes, 138,670 triangles, 465,164 rays, all from placement_leaf and placement_organic.
  • Cliff: clifflab/rockpile.py 1×1 seed 1, from this branch's copy. 175 scenes up to 2.6 M triangles, 11.4 M triangles in all, 18.4 M rays: _relief 16.3 M, _grain 2.1 M, _dirt_layer 19.6 k.

crates/dt-geom/examples/r3_rays.rs replays them in the same frame. Embree's times come from the same capture replayed through embreex 4.4. Embree builds with TBB on all cores, and embreex queries on one thread, so the build ratio compares multi-threaded builds and the query ratio compares single threads. Timings are the best of 5 runs for the tree and of 1 for the cliff.

The two seed-7 disagreements are one far ray (0.080 mm) and one hit-vs-miss, both in _drive_batched; the brute-force re-cast sides with obvhs on both, and both flip under a 1e-4 mm nudge, so they are grazing rays like the cliff's. The distance differences are on identical hits and are float32 rounding of the hit parameter: Embree and obvhs order the same arithmetic differently, and at the tree's 70 mm frame one float32 ulp is about 8e-6 mm. The gate's 1e-4 mm clause was set too tight for float32 data; it passes on one capture of three. What the leaf placer needs is the same triangle (it is) and distances well inside its own tolerances (its smallest is the 0.24 mm leaf thickness, about 1,300× larger). P5 judges trees on metrics and renders, and the plan's ray gate is restated as ≥ 99.9% identical hits with max Δt ≤ 1e-3 mm.

"Identical" means the same triangle, or both miss. "Max Δt" is the largest distance difference on identical hits, converted to mm. Deterministic means the structure hash is equal at 1, 4 and 16 threads and across runs, and the 12-thread query returns exactly the 1-thread answers. On 12 threads, the queries run in 0.41–0.44× Embree's single-threaded time.

By label, for obvhs medium: _grain is 99.9998% identical (2 hit-vs-miss rays in 2.05 M); _dirt_layer is 98.46% identical plus 1.53% ties; _relief is 99.05% identical. Every backend is deterministic on the cliff too.

1. An obvhs bug, worked around

Unpatched obvhs lost 8.6 M of the relief rays. Those rays are horizontal, built as -cos(a)·m − sin(a)·z with a = 0, so their z component is -0.0. obvhs 0.4's safe_inverse(-0.0) returns -1/ε, but its octant test reads -0.0 < 0 as false. The slab bounds swap, and the ray misses every node. ObvhsRays adds +0.0 to each direction component, which turns -0.0 into +0.0 and changes nothing else. A unit test covers it. The bug should go upstream.

2. What is left is rounding on grazing rays

A referee in r3_rays.rs re-casts a sample of the disagreeing rays by brute force (every triangle, a Rust port of Embree's triangle test, no BVH), then nudges each origin by 1e-4 mm in six directions and re-casts the nudged rays the same way, to see whether the answer changes. Embree itself was not re-run on the nudged rays. The sample is 385 of the 20,762 far and hit-vs-miss disagreements for obvhs medium (about 1.9%); the 0.73% of rays that are ties within 1e-4 mm were not refereed.

Almost every disagreement is an axis-aligned ray from rockpile's relief grid, grazing faces that sit on the same grid. In the brute-force re-cast (a Rust port of Embree's triangle test over every triangle; Embree itself was not re-run), the answer changes when the origin moves by 1e-4 mm, so on the sampled rays neither Embree's answer nor ours is a stable one. On these rays the re-cast agrees with obvhs, which uses the same port of the test, so the re-cast shows instability, not which answer is right; ties were not refereed. parry's own triangle test rounds differently, which is why it disagrees about four times as often.

What this changes in the plan

  1. R3 is retired for the leaf placer, with the distance clause relaxed to 1e-3 mm (see three captures). The trees phase can rely on obvhs behind Rays. Measured again in revision 7 (2×2-grass-tree, both systems, 3 runs): leaf placement takes 3.4–4.0 s per scale, 7.1–7.7 s of a 17.2–18.3 s tile build (median 17.6 s), not the 11.3 s of Embree time quoted in feasibility.
  2. The cliff port should not cast exactly grazing rays. rockpile's _relief grid lines up with the mesh it casts at, so about 0.8% of its answers are rounding noise (their answers flip under a 1e-4 mm nudge in a brute-force re-cast with a port of Embree's test). In Rust, offset the grid off the mesh's own lattice (as overhang_faces already does) or use the depth-peel raster suggested in feasibility. Cliff parity is then judged on metrics and renders, not on ray-for-ray agreement.
  3. Every direction vector goes through Rays. The -0.0 workaround lives in ObvhsRays. No caller should use obvhs directly.
  4. Parallel speed comes from queries, not builds. Batch queries scale 6–7× on 12 threads. obvhs builds don't scale at these sizes, and they are already faster than Embree's.

Parity harness, Python half

tests/parity/run_lab.py builds dirtlab 2×2 at seeds 1–4. For each seed it writes the STL, a metrics.json, and four renders (painted, top, low, 20 mm close-up) with overhang faces painted red, using clifflab's layer-reach audit at 55°. It finishes with one contact sheet. Output goes to out/parity/dirt/, which is gitignored. It renders through dharmatiles.render and falls back to a CPU Embree renderer with the same camera and lights when pyrender has no screen; this run used the fallback. A full run takes 95 s.

The metrics are computed from the STL alone, so the Rust half can run the same function. These are the plan's metrics that apply to dirt:

The bare fraction uses a top-hat estimator (a 6 mm grey opening, with cover where the surface stands 0.35 mm above it). It counts tall clods as cover, so it reads lower than dirtlab's own pebble mask, shown as "lab truth". It is stable across seeds (0.771–0.792), and it is the same function on both sides, which is what parity needs.
