What each result changes in the plan

These changes are made in this revision on the plan and feasibility pages. Each is listed in the change log under revision 6.

R1 booleans

  1. The mesh backend is manifold-csg 0.4.1, with Manifold's parallelism on. Without TBB it takes 3–5× Python's time on the cliff; with TBB it matches. The old design note "run each boolean single-threaded and many in parallel" is dropped: it is not needed for identity on one machine and it costs 3–4× on the cliff's big unions.
  2. manifold-rust stays behind the trait as the browser backend only. Its wasm build compiles in CI. It is re-measured with r1_replay --backend port when Python moves to Manifold 3.5.4 or the port's parallel speed improves.
  3. Kernel rule: keep solids inside the kernel between operations. manifold-csg's C API cannot pass face IDs back in, so a round trip through a plain triangle mesh loses coplanar-face grouping and the material chain R9 relies on.
  4. The parity harness compares metrics and renders against a Python replay, never bytes. Even Python against itself, re-importing the same operands, changes the triangles on about 9% of cliff results, and Python's Manifold (3.5.1) is a different version from manifold-csg's (3.5.3).
  5. The cliff's speed must come from outside the booleans. Booleans are about 11% of the rockpile build and 14–20% of the massif. The kill criterion (cliff batch within 2× Python) is met, but the P7 targets (1×1 in ≤ 15 s, massif in ≤ 60 s) rest on porting the Python and numpy remainder well: adaptive heightfields and parallel stones.

R2 determinism

  1. Kernel rule: assign original IDs in index order before combining parts made in parallel. Manifold numbers solids from a process-wide counter, so parts built on several threads get IDs in scheduling order, and a boolean orders its output by ID. Calling as_original() in index order before the batch fixed the only thread-dependent result found.
  2. Use the libm crate, not std's sin, exp and powf, in seeded code. The platform maths library gave three different hashes on three platforms; everything else we wrote matched on all three.
  3. The P1 hash gate depends on your level choice (decision 1 below). With the recommended level, golden hashes are shared by the macOS and Linux CI jobs, and Windows checks thread identity plus metrics.

R3 rays

  1. The ray backend is obvhs 0.4 with Embree's triangle test and medium_build; parry3d 0.31 stays behind the same trait as the spare. The embree3 FFI fallback is dropped from the plan: no maintained binding exists, and none is needed.
  2. Route every ray through our Rays wrapper. obvhs 0.4 loses rays whose direction has a -0.0 component (8.6M of the cliff's relief rays). The wrapper adds +0.0 to each component, which fixes it and changes nothing else. No caller uses obvhs directly.
  3. The cliff port does not cast exactly grazing rays. rockpile's relief grid lines up with the mesh it casts at, so about 0.8% of its answers are rounding noise in Embree as well. In Rust, offset that grid off the mesh lattice or use the depth-peel raster; cliff parity is judged on metrics and renders, not ray for ray.
  4. Leaf placement in Python now takes about 4 s, not the 11.3 s of Embree time the feasibility page quoted. The tree speedup in P5 has less to win from rays than assumed. Batch queries scale 6–7× on 12 threads, so that is where the parallel gain is.

R6 format

  1. dt-doc exists and is the P1 starting point: kdl 6.7.1 (KDL v2, its v1 features off), a hand-written decoder with one function per node type, one control table per look, byte spans on every name and value, and miette errors that keep going past the first mistake. It builds for wasm32-unknown-unknown, which CI now checks.
  2. Two design gaps for later phases. Meadow needs the species controls the tiles set (length, curl, clearance, clumps) or a ruling that they go (P4). cliff along=… must either be limited to tile edges or rockpile's band forms generalised to any line (P7).
  3. The syntax may still change before P1, depending on your answers. The plan's R6 fallback (change the syntax before P1) is the route for any answer that differs from what the tiles do today; the decoder is small enough that this costs days, not weeks.

R9 materials

  1. Colour rides on original IDs for solids, and on (original ID, face ID) back to a co-sampled material field for level sets. The fallback the plan listed is now simply the method. P3 still retires R9 in production on real rocks and water.

Decisions for you

Each decision has a recommendation. "Blocks" says which phase needs the answer.

1. Determinism level (R2) · blocks P1

The confirmed default 2 is "byte-identical on one machine; visually identical across machines". R2 shows more is possible for free on two of the three platforms. The options:

  • A. One machine only. Golden hashes per platform, each checked only against itself. Cheapest, but three sets of hashes to keep.
  • B. macOS and Linux share byte hashes; Windows is gated on metrics and renders. One golden set, checked on both the Mac and Linux CI jobs. Windows runs the thread-identity test, the golden summaries' metrics (triangle count, volume, overhang, holes) and the render gate, but not the byte hashes.
  • C. All three platforms byte-identical. Would need Manifold's own sin/cos calls replaced inside both the C++ and the Rust port. Not worth it.
Recommendation: B. It costs nothing beyond the libm rule, catches a whole class of accidental changes on two platforms, and asks nothing of Windows that R2 showed it cannot give. You print from the Mac, and CI runs Linux on every push.

3. Reinstall rustup natively on the Mac · blocks nothing, recommended before P1

The rustup and cargo proxies in ~/.cargo/bin are x86_64 binaries running under Rosetta (rustup itself warns "Rustup is not running natively"). The compiler they launch is the native arm64 1.99.1, but the build scripts they start inherit the emulated architecture. In R1 that made the cmake build of Manifold compile x86_64 objects into an arm64 binary, which failed to link. The spikes worked around it by putting ~/.rustup/toolchains/1.99.1-aarch64-apple-darwin/bin first in PATH.

Recommendation: reinstall rustup natively (the arm64 installer from rustup.rs; it keeps ~/.rustup and the pinned toolchain). It takes a few minutes, removes the PATH workaround every agent would otherwise need, and keeps local timings native. It needs your go-ahead because it changes your machine's setup.

4. The contact sheet draft · blocks P1's harness work

The Python half of the parity harness exists: python tests/parity/run_lab.py builds dirtlab 2×2 at seeds 1–4 in about 95 s and writes, per seed, the STL, a metrics.json and four renders (painted, top, low, 20 mm close-up) with overhangs painted red, then one contact sheet into out/parity/dirt/ (not in git). Its bare-fraction estimator reads lower than dirtlab's own pebble mask (0.77–0.79 against 0.92–0.93) because it counts tall clods as cover; it is stable across seeds, and both sides will run the same function.

Recommendation: approve the layout (four views per seed, overhangs red, one sheet per look), or say what you want to see side by side. P1 adds the Rust column next to it.

Choices the agents made, for your veto

These follow directly from the measurements. They need no action unless you disagree.

  • manifold-csg 0.4.1 is the default mesh backend, with Manifold's parallelism on (the manifold-parallel feature).
  • manifold-rust stays the browser backend only; the browser build stays in P8.
  • obvhs 0.4 (medium_build) is the ray backend, parry3d the spare; embree3 is dropped from the plan.
  • The four rules above: original IDs in index order, solids stay in the kernel, libm in seeded code, every ray through Rays.
  • The parity harness compares metrics and renders against Python, never bytes.
