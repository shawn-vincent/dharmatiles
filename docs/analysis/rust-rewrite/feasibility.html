Will it work in Rust?

Yes, with six risks that each need a short spike before the port starts. The geometry engine the labs depend on, Manifold, has a maintained Rust binding and a credible pure-Rust port. Everything else is either a mature crate or under 150 lines to write. The biggest speedups come from parallel blade meshing and from better algorithms, not from the language alone: Python already calls Manifold's C++.

Phase 0 measured it. On 1 Nov 2026 the spikes answered R1 booleans, R2 determinism, R3 rays and R9 materials with a go; R6, the format, waits on Shawn's read. The results replace the assumptions below where they differ. Verdicts and the decisions left to Shawn are on the go/no-go page.

Recommendation: start on manifold-csg, because it is the same engine as today's Python manifold3d, so the port changes no geometry behaviour. Keep the mesh kernel behind one trait so manifold-rust can replace it once the R1 spike shows parity. That would remove the C++ toolchain and give deterministic parallel booleans.

Result (R1, report): ship manifold-csg with Manifold's parallelism on (the manifold-parallel feature, default). manifold-rust stays behind the trait as the browser backend, and is re-measured with the same replay when Python moves to Manifold 3.5.4 or the port's parallel speed improves. The replay ran at a larger scale than planned: single meshes up to 7.1M triangles and a 202-part, 13.2M-triangle union on the massif, at 12.2 GB peak memory. Two kernel rules came out of it. Keep solids inside the kernel between operations: a round trip through a plain triangle mesh loses face IDs, because manifold-csg cannot pass them back in. And assign original IDs in index order before combining parts made in parallel (see determinism below). The C++ build adds about 5 minutes to a cold CI run and nothing much to a cached one.

Heightfields stay grids until the last moment

Ground, water, dirt, cliff support, seats and face relief are all f32 grids that are lifted to solids at the end. A lifted heightfield is watertight by construction (top, walls, bottom). The rewrite should use adaptive triangulation (error-bounded, in the style of RTIN or greedy insertion) everywhere instead of the uniform 0.1–0.2 mm meshes used today. That is the single biggest cut in mesh size for cliffs and water, and therefore in boolean time. Grids need one convention: the library has three (core/mesh.py:69, water.py:542, core/grid.py), which drift by up to one cell.

Watertight, every time

Three layers, the same as the labs today. By construction: lift, loft and convex carving produce closed solids without booleans. By kernel: Manifold guarantees a manifold result for manifold inputs. At export: reload as float32, separate pinches, keep the largest body, and audit overhangs. This step is a gate, because round 11 cliffs still have residual overhang and some see-through gaps. Notably, rockpile and grasslab already keep only the largest body, which silently drops anything that came loose. The Rust audit should report what was dropped.

Determinism across threads

  • Seeds by key, not by stream. Hash (seed, item index, salt) with xxhash or splitmix and write the uniform and normal transforms yourself. Never rely on rand::StdRng; its stream is not stable across versions. Use rand_chacha or rand_pcg where a stream is needed.
  • Order-dependent solvers run sequentially within their entry: the gravity partition, the crack network, the coverage filler and the leaf standoff stack. Independent items (blades, stones, rocks) run in parallel.
  • Reductions in fixed order. Rayon's map/collect keeps order; its float sum does not. Split into fixed chunks and combine in index order.
  • Manifold: its maintainers state that with parallelism off, run-to-run output is identical; with it on, CSG scheduling is not deterministic (issue #1177). The plan was therefore to run each boolean single-threaded and many booleans in parallel. R2 measured otherwise: with parallelism on, every stage hash was identical at 1, 4 and 16 threads, and two runs of all 21,476 cliff booleans gave the same whole-run hash. The one thread-dependent result came from Manifold's process-wide original-ID counter: parts built in parallel get IDs in scheduling order, and a boolean orders its output triangles by ID. The rule is to assign original IDs in index order (as_original()) before combining parts made in parallel. Parallelism stays on, because it is 3–5× faster on the cliff. Pin the Manifold version, because decimation and triangulation change between releases.
  • Floats: Rust does not fuse multiply-adds implicitly, so basic arithmetic matches on x86 and ARM. sin, exp and powf come from the platform maths library and differ between platforms: R2 got three different hashes on macOS, Linux and Windows for the same sin/exp stage, while noise, scatter and EDT matched on all three. Use the libm crate, not std, in all seeded code.
  • Resolution-independent noise. The library draws random cell indices and white noise on grids, so the same seed gives a different tile at a different resolution. The rewrite keys noise by position so previews, finals and the OpenLOCK build agree.

Hosting the description language

Recommendation: KDL documents decoded into a typed Rust model. From that model, generate a JSON Schema (for example with schemars), which becomes the single contract for CLI validation, GUI forms and MCP tool inputs. Values use one small hand-written expression grammar: arithmetic on parameters, distributions ("a..b^k"), named heights and field constructors. No loops, assignments or nested call chains. Write a build record (document hash, seed, engine version) into each STL and 3MF so CLI, GUI and agent builds can be compared. The cost: today's .tile.py files use Python helpers and shared constants. Definitions and the library directory have to replace them, which spike R6 tests on three real tiles.

Result (R6, report): the three tiles are written in KDL v2 and decoded by the new dt-doc crate with kdl 6.7.1 (v1 features off) and miette, by hand, with no derive crate. Every value the Python sets survives, every file prints back byte-identical, and an edit changes only the value's own text. Two things learned about KDL v2: ranges and percents must be quoted (size="1..6^2"), and the crate's own parse messages are generic, so dt-doc rewrites the common ones. The format waits on Shawn's read and eight syntax questions.

Live preview

edit KDL→parse + check · ms→plan pass · < 1 s→2D / height preview→build changed entries→mesh preview→union + export on request
  • Cache by entry. Key each entry's plan and solids by (path, seed, hash of what it read). An edit rebuilds the entry and whatever reads it; everything else is a cache hit. Typst's comemo crate does this kind of tracked memoisation; salsa is heavier.
  • The plan pass is the live view. Regions, footprints, flow lines, clearings and height fields draw instantly. Solids follow per entry, and the final union happens only on export.
  • Viewer. A Tauri webview with three.js matches the GUI Shawn leaned toward. The same web front end (app/ui) is also served to any browser by dharmatiles preview, so there is one viewer for the desktop app, the phone app and the browser (layout page). notify watches files for hot reload; rerun is a ready-made viewer for debugging stages during the port.
  • Limit: changing the tile seed or an entry at the bottom of the stack invalidates everything above it that reads it. Hills are read by almost everything.

Browser and phone builds

Everything except the mesh kernel is pure Rust and compiles for the browser (wasm32-unknown-unknown) and for phones. The mesh kernel is the exception. manifold-csg-sys 3.5.100 is tested on wasm32-unknown-emscripten, but the plain browser target is provisional, behind an unstable-wasm-uu feature, and the emscripten target does not mix well with wasm-bindgen. A browser build therefore realistically needs manifold-rust. Since R1, CI builds dt-geom with manifold-rust for wasm32-unknown-unknown in full, and checks dt-doc for the same target; both pass. iOS and Android builds of the C++ are probably fine through CMake but unverified. The crate split keeps this open at low cost: the backend is a feature of dt-geom only, dt-doc has no geometry at all, dt-eval reads files through a source trait, and one CI line (cargo check -p dt-eval --target wasm32-unknown-unknown --no-default-features --features manifold-rust) fails as soon as the core picks up a native-only dependency.

Migration path

Python stays the reference throughout, and each phase ends with a tile Shawn can print.

Where the code goes (layout page): the Cargo workspace sits at the repo root from phase 0, beside the Python, which stays exactly where it is (src/, tests/, the labs, stl/). Rust writes to out/, so a side-by-side comparison is two folders. Each .tile.py in src/tiles/ is rewritten by hand as library/tiles/<family>/<name>.kdl in the phase that ports its looks, and deleted once its KDL twin passes review. At cutover the Python is removed and kept in history under a tag.

What I could not verify

  • manifold-rust's parity for refine and smooth_out. (Resolved by R1: vertex properties and original IDs match through booleans; its parallel output is bit-identical to sequential; its speed on multi-million-triangle unions is 2.0–3.7× Python's.)
  • A benchmark of obvhs against Embree, and whether obvhs builds deterministically. (Resolved by R3: 2.4–2.6× Embree single-threaded on the leaf placer's rays, and identical builds at 1, 4 and 16 threads.)
  • Whether Manifold is identical across x86 and ARM in general. (Measured by R2 on one test pipeline, with parallelism on: macOS-arm64 and Linux-x86_64 match byte for byte, Windows-x86_64 does not.)
  • The quality of baby_shark's remesher; whether facet-kdl supports KDL v2 well enough to replace hand decoding.
  • Whether manifold-csg cross-compiles for iOS and Android through CMake.
  • The exact parts of a Bambu project 3MF (from memory: core 3MF plus model and project settings files and per-triangle paint attributes).
  • The 10× estimate for blade meshing. It comes from the per-blade profile and the core count, not from a measurement.
