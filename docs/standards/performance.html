Standard · building, checking, the tests

Performance

The work is many small changes in quick succession, so the time to build and check one is kept like correctness. Each cycle has a budget; the checks time themselves against it and say when they are over; an over-budget cycle is the next task. This page is the budgets, where the time goes now, and how to measure it.

The budgets

CycleThe commandBudget
Warm build after an editcargo build --releaseunder 1 minute (seconds is the aim)
The checks, as work goes on and before each mergecargo xtask checkunder 2 minutes (CHECK_BUDGET)
Cold build from a fresh clone or worktreecargo build --release in an empty target folderunder 5 minutes
Everything, before a push or a releasecargo xtask check --fullabout 10 minutes (FULL_BUDGET)

Times are measured on an idle machine (the development Mac: 12 cores, 8 performance and 4 efficiency, 64 GB). Every cargo xtask command is timed against its budget, and so is each step of check. The build is a step of its own, held to the warm build's budget, or the cold build's in a checkout with no release build yet, so the steps after it time only their own work. Each prints its time, a run past its budget prints an OVER BUDGET banner on both streams, and every run (time, worktree, what, seconds, budget) is logged to dt-times.tsv in the git common folder, so every worktree's runs are in one file. The program's build and the tests' build the engine with the same features (no feature is on by default, Manifold's parallelism follows the target, wasm-bindgen is a browser dependency only, insta has no colours, and the program asks for rustix's fs as the tests' tempfile does), so after an engine change the program's build compiles only its own crate (7 s, from rebuilding dt-eval through dharmatiles); dt-crash-switch is the one intended difference. To check after changing a dependency, compare the two builds' --message-format=json artifacts: every crate should have the same features. A check ends with each step's time against its budget on one screen. Its tests run in two lanes (xtask/src/lanes.rs): dt-eval’s tile tests beside every other test binary, each binary’s time printed. The gain is small, 63 s to 58 for an engine change, because the tile tests already fill the cores: the tests are CPU-bound, and the next saving is in what the torture set builds. The budgets are one table, xtask/src/budget.rs, and are raised only by editing it.

The tests: a torture set, each tile built once

  • A test never builds what a test already built. dt-eval's integration tests are one test binary (crates/dt-eval/tests/tiles/, a module for each file) and build only through one memo (memo::build, from the dev crate dt-testkit), keyed by everything a build reads: the source's content, the path, every field of Options. A scan test fails a build outside it unless a // fresh: why comment says the test must build again (the cache, thread counts, a build compared with itself).
  • The warm check builds the torture set only. golden::TILES in crates/dt-eval/tests/tiles/golden.rs: about thirty small test tiles, each held to its stage hashes, repair counts and the gate's verdict. A warm test that reads any other test tile fails, by construction (the memo checks the test's name). A test that needs another tile is a thorough_ test: ignored, with a reason saying so, and run by check --full.
  • --full runs dt-eval once. Its warm tests, its thorough tests and the library baseline (the sweep) are one run of the one test binary, so a tile any of them reads is built once even there. Only the release gate (every library tile on both systems, which cargo xtask release runs) and a measurement are left out (NOT_CHECKS in xtask/src/work.rs).
  • Any run at another seed. DT_TEST_SEED=N (on cargo xtask check, sweep or cargo test) builds every tile a test builds on seed N, unless the test sets a seed itself; the snapshots and the library baseline, recorded at each tile's own seed, are then held only to the gate's pass or fail and the repair budgets, and a baseline rewrite is refused. The library at seed 9001 takes the sweep's time again (about two minutes), not four times the library.
  • Test builds run several at once. A memo build runs on its own two-thread pool (so the pool is never the whole machine, and a match with the golden hashes, recorded from plain builds, proves threads change nothing), and memo::prebuild builds a list of tiles six at a time.

Where a build's time goes

A build is mostly serial: alone on the machine, the biggest library tile (cliffs/2x2-cliff-corner, 22.5 s) keeps 4.6 of the 12 cores busy on average. Its peak memory is 8.2 GB; the 2×2 wall curve's 7.1 GB, the 2×2 grass and tree's 5.8 GB.

Library tile, aloneBuildThe stages that take the time
cliffs/2x2-cliff-corner21 scliff 10.7 s, audit 3.5, union 2.8, dirt 2.1
walls/2x2-wall-curve14 sunion 7.2 s, grass 2.4, audit 2.2, wall 1.3
ground/2x2-grass-tree14 sunion 6.5 s, tree 2.7, grass 2.5, audit 2.1

The cliff's CPU, sampled: about half is Manifold (the booleans that carve each stone and the union), a fifth is ray casting (the relief pass: for each stone and each of its faces, at two angles, a ray grid over the face against the stone's mesh, through obvhs), the rest the element's own code. The cliff dresses its columns in parallel and the stones of one column in order, so one tall column sets how long the stage takes. The union is Manifold's batch boolean over every solid in the scene, in source order.

The library sweep

The library baseline (crates/dt-eval/tests/tiles/baseline.rs, held to crates/dt-eval/tests/baseline/library-db.tsv) builds every library tile on DungeonBlocks once, on the seed it writes: sixty builds. Its repair budgets were recorded as the worst of four seeds, which leaves room for the counts' noise; the counts are held to them on the one seed. It is CPU-bound: the builds run on WORKERS threads at once, longest first, each build spreading over the machine inside; five fill the machine (the cliff tiles: 300 s on three workers, 251 on five, 250 on six, the same 2,230 s of CPU each), and five of the biggest builds together are 41 GB. The cliff tiles are about half the sweep.

So the sweep is made faster only by building less or by building faster: the engine's own time (the cliff's stones, Manifold's booleans, the relief rays) is what it is made of. cargo xtask sweep grass sweeps only the tiles that use an element; the check sweeps only the library tiles a change touches.

How to measure

To seeRun
A command's wall time and CPU time/usr/bin/time -p <command>: CPU time over wall time is how many cores it kept busy
Its peak memory/usr/bin/time -l <command>: maximum resident set size
A build's stagesdharmatiles build <tile> --no-cache --json: stage_secs, each element of the stack and the union, lift and audit
Where a build's CPU goesstart the build in the background and run sample <pid> 18 1 -file out.txt (macOS): the call tree, and the functions by samples at the top of the stack; leave out the waits (__psynch_cvwait, semaphore_wait_trap, swtch_pri, TBB's backoff) to read the busy share
The sweep at another pool shapeDT_BASELINE_ONLY=cliff (an element's tiles, or lib: paths) on the_library_builds_as_the_baseline_says, with WORKERS changed
Which test spends a test binary's build timelog each build's thread name (the test's name), path and seconds from build_checked for one run, and sum by test
The checks' historydt-times.tsv in the git common folder (git rev-parse --git-common-dir)

Measure on an idle machine, one heavy job at a time (the heavy-job lock: cargo xtask heavy <command>), and time the real commands. Find the cause before optimising: load from too many parallel jobs, the same thing built twice, network fetches in builds, and checks sized for the biggest possible change are the usual ones.

Choosing the torture set by coverage

The torture set is the fewest tiles that run the most of the engine. To choose it again (after a new element, say):

  1. Build the program with coverage on the workspace's crates only (instrumenting the dependencies too, Manifold's bindings among them, makes a build four times slower): a RUSTC_WORKSPACE_WRAPPER script that adds -C instrument-coverage, and its own CARGO_TARGET_DIR. The toolchain's llvm-tools component has llvm-profdata and llvm-cov.
  2. Build each test tile once with LLVM_PROFILE_FILE set to a file of its own (and the OpenLOCK and other tiers a test reads), timing each.
  3. For each: llvm-profdata merge, then llvm-cov export -format=lcov, and keep the lines run in the engine's crates (dt-geom, dt-kit, dt-elements, dt-eval, dt-doc, dt-value, dt-lang).
  4. Choose greedily: each time, the tile that runs the most lines the chosen ones do not, per second of building, until the set reaches 99.5% of what all the test tiles run together. Weighting by build time matters: it picks small tiles over big ones that run the same code. Where only a big tile reaches some code, write a small tile that does (that is how 1x1-grove-small and 1x1-reeds came to be) and run the choice again.
  5. Add what line counts cannot see: the odd shapes (a 3×1 zigzag, a 1×2 diagonal, a corner sliver), and a small tile for any feature a warm test reads that no chosen tile has.

A new tile's hash snapshot is checked against a plain build (no observers, the whole machine) before it is committed: that the memo's two-thread, observed build matches it is the proof that threads and observers change nothing.

Rules

  • An over-budget cycle is the next task, straight after the current one and ahead of the queue. It is fixed where the waste is made, never by skipping a check or loosening the gate.
  • Slowness is visible by construction: every command and every step of a check is timed against its budget and says when it is over.
  • Checks are sized to the change while working (cargo xtask check); the full set runs once before a push (--full).
  • At most two heavy jobs on the machine at once: two agents, and the heavy-job lock for sweeps, contact sheets, pictures and the browser build.
  • A warm test reads only the torture set; a new element or feature gets a small torture tile, and its test reads that.
