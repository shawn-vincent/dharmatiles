Errors

Nothing is swallowed and nothing is hidden. When something goes wrong you see it, in words, with what to do next. A tile that fails loudly gets fixed; a tile that quietly comes out different gets printed, and costs a spool and an evening.

Two kinds of error

Expected: your document or your inputUnexpected: the program
What it isSomething you wrote or did that the program checks for and refusesSomething broke: a bug, a panic, a file the program could not read or write, a kernel that failed
ExamplesAn unknown control (dt::unknown-control), a value out of range, a read nothing in the stack writes, a tile that fails the printability gate, an old form that needs dharmatiles migrateA panic in an element, a Manifold failure, an I/O error writing an STL, a malformed reply from the preview's server, a build worker that died

Telling them apart

An error is expected only when all four hold:

  1. The program checks for it explicitly, and it has a name: a dt:: diagnostic code, or a gate verdict.
  2. You can fix it yourself by changing the document or what you typed.
  3. Nothing is broken: the program did exactly what it should.
  4. The message says what to do: a help line, a suggestion, or the numbers that failed.

If any one fails, it is unexpected. When in doubt, treat it as unexpected: a loud report of something minor costs a minute, a silent one can cost a print.

One operation can fail both ways. Building a tile can be refused by its document (expected) or crash in a kernel (unexpected). Keep them apart by type, never by catching everything: document errors are diagnostics with codes, everything else is an error that carries its cause. Never show a kernel failure as if it were a mistake in the tile.

Where errors are handled

Below the boundaries an error travels up, unchanged except for added context. It is handled only at a boundary, where someone can be told:

BoundaryWhat it does
The command line (main)Prints diagnostics with miette (code, span, help) and other errors with their chain of causes, to stderr; exits 1
The preview's HTTP routesAnswer a document error as data the page shows inline; answer anything else with an error status and a body naming what failed and why; log it to the server's stderr
The preview's build workerCatches a panic per build, reports it to the page as a failed build with its message, logs it, and keeps serving; the next edit builds again
Library sweeps (build --all)Report every failing tile by name with its reason and carry on to the next; the run exits 1 if any failed
The page's event handlersShow an unexpected failure in the error panel or the connection chip; never only in the console

In the Rust code

  • Return Result and use ?. Add context where it helps (which tile, which element, which file) rather than replacing the error.
  • Document errors are miette diagnostics with a dt:: code, the span, and a help line. A new refusal gets a new code, not a reused vague one.
  • No let _ =, .ok(), unwrap_or_default() or unwrap_or(…) on a result that can fail for real. Writing into a String cannot fail, so let _ = write!(s, …) there is fine.
  • unwrap and expect only for what cannot happen; an expect message says why it cannot. Anything a document or a file can cause is a Result.
  • A panic is a bug. It is never part of the plan, and a caught panic is still reported.

In the preview

  • Document errors appear beside their line and in the error panel, with the program's message and help. The page never re-checks a document itself; it asks the program (/api/check-value, the build) and draws the answer.
  • An unexpected failure (a server error, an unreadable reply, a failed fetch other than the connection dropping) goes to the error panel with what was being done ("Could not save 1x1-cliff-corner") and the error's words. Logging it to the console as well is fine; logging it only there is not.
  • A lost connection is shown by the connection chip, and the page tries again. That is expected, so it is not an error panel entry.
  • Unhandled promise rejections and script errors are caught globally and shown the same way.

The few allowed silences

An error may go unshown only when it changes nothing you make or see, and the code says why in a comment where it is ignored:

  • Per-viewer conveniences in the browser: localStorage can be unavailable (private windows); a remembered theme, layout or toggle then falls back to its default.
  • Best-effort cleanup: removing a temporary file or an empty cache folder after the real work has succeeded.
  • You cancelled: closing a picker or a menu is not an error.
  • Offline: a request made while the connection is down, which the page repeats on reconnect, with the chip showing the state.

Output never changes silently

No fallback may quietly change what is built. If a value cannot be read, the tile is refused; it is never built with a default instead. If a repair changes the mesh (voids filled, pinches moved), the build says so and the build record counts it. The printability gate is never loosened and geometry is never culled to pass it. What prints is what the document says, or the program says why not.

Tests

  • Every dt:: refusal has a test that a document triggers it, with its code.
  • The preview's server has tests that a document error comes back as data and an internal failure as an error status with its message.
  • A panic anywhere in a test run is a failure, never retried away. An intermittent crash is a bug to find (the Manifold level-set fix is the model: reproduce, find the cause, prove the fix).
