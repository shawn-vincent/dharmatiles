# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Project Does

**dharmatiles** builds procedural 3D-printable terrain tiles as STL files from short `.dtile` documents (the tile language, KDL v2 underneath). Each tile has a DungeonBlocks-compatible socket-peg underside (or an OpenLOCK clip base), dirt with clods and pebbles, rocks, grass blades, water, walls, floors and trees. Tiles are for tabletop gaming (35 mm square grid, DungeonBlocks standard; OpenLOCK is 25.4 mm). Every build runs through a printability gate: watertight after the float32 reload, no lost parts, overhang held to 55 degrees (small budgeted patches to 65 and past it).

dharmatiles is a pure Rust program (the `dharmatiles` binary). The only other code is `extras/`: a paint organizer, its stand and two STL helpers, standalone Python scripts that are not part of the program. The Python library, the labs, the parity harness and the old design history were deleted on 4 Nov 2026; the tag `before-rust-only` holds them. New elements are designed in Rust.

## Commands

```bash
cargo build --release                      # the dharmatiles binary: target/release/dharmatiles
dharmatiles build lib:tiles/ground/1x1-grass.dtile          # one library tile  -> out/db/ground/1x1-grass-db.stl
dharmatiles build my-tile.dtile --system ol --png            # a file, for OpenLOCK, with four preview PNGs (overhang red); --printer NAME picks a profile from library/printers/ or $DT_HOME/printers/
dharmatiles build my-tile.dtile --3mf                        # also a 3MF painted by material; a Bambu Studio project when ~/dharmatiles/bambu.3mf (or --bambu-template) exists
dharmatiles build --all [--system ol] [--printer fine]       # every library tile for one target -> out/<system>[-<printer>]/<group>/ (one build is one target; there is no `both`)
dharmatiles check my-tile.dtile [--system ol] [--printer NAME] [--seed N]   # read and plan only, for one build target
dharmatiles inventory [list|have <tile>|gone <tile>|relink <old> <new>]   # what you have printed: inventory.dinv in My tiles, a log; plates print only what it lacks (plates --all ignores it)
dharmatiles elements [name]                                # the elements and their controls
dharmatiles explain dt::type                               # what an error code means, from the local copy of its docs/e/ page (every error prints this command and its online address)
dharmatiles watch my-tile.dtile                              # rebuild on every save
dharmatiles preview my-tile.dtile --open                     # live painted 3D view in the browser (127.0.0.1:7878); overhang red; also takes .stl
dharmatiles                                                 # no command = preview --open: browse My tiles ($DT_HOME, else ~/dharmatiles) and the Library; folders as args work too

cargo test --release --workspace            # all tests (insta golden hashes included), under 5 minutes
cargo test --release -p dt-eval --test tiles -- --ignored every_library_tile_passes   # release check: every library tile through the gate on both systems (name both tests in one command and the DungeonBlocks builds are made once for the two)
cargo test --release -p dt-eval --test tiles -- --ignored the_library_builds_as_the_baseline_says   # every library tile on DungeonBlocks against tests/baseline/library-db.tsv (hash, triangles, repairs, overhang, and each tile's repair budget: a repair count on the tile's own seed above its `max_*` fails, and a rewrite can only lower a budget); DT_BASELINE=write rewrites it; about 3 minutes
DT_TEST_SEED=7 cargo xtask check           # any test run at another seed: every tile a test builds is built on seed 7 (a test that sets its own seed keeps it); snapshots and the baseline, recorded at each tile's own seed, are held only to the gate's pass/fail and the repair budgets, and are never rewritten at another seed
cargo clippy --release --workspace --all-targets -- -D warnings   # release, like the tests: one build of Manifold and the engine (dev builds both again, about 3 minutes cold)
cargo fmt --check
cargo xtask sheet <tile|name> [--seeds …] [--system ol]  # contact sheet: four views per seed, seeds 1-4 -> out/sheet/<tile>/contact-sheet.png
cargo xtask pictures [group …]              # rebuild the element pages' pictures from docs/elements/demo/
cargo xtask docs [--check]                  # fill docs/elements/ pages' controls tables from the element schema; write the #dt-<code> anchors (from data-explains markers) and docs/e/<code>.html error pages; --check also fails on a code with no explaining section, a marker naming no code, or a stale page
cargo xtask release 0.10.0 "<summary>"      # fold docs/changelog.d/ into a numbered changelog entry, bump Cargo.toml, check, commit, tag v0.10.0, push; needs an audit commit (touching only ledger.kdl) since the last tag, and `--skip tests|audit "<reason>"` overrides one check and writes the reason into the entry
cargo xtask check [--full] [--plan]         # the checks this branch's changes can fail (tests from one queue, the slowest binary of the last run first; --plan names the packages a change selects), chosen from its diff against main (merge on this): an element or geometry change is held by the torture set's goldens, not the library; --full is everything, the thorough tests and the whole-library sweep included (one run of dt-eval's test binary), before a push
cargo xtask sweep [grass|lib:tiles/… …]     # the baseline for the tiles that use those elements (all when none named); a heavy job
cargo xtask heavy <command …>               # run a machine-loading command once no other heavy job runs in any worktree (sweep, sheet, pictures, wasm take the same lock)
cargo xtask editor [--site|--page] <out-dir>  # the editor page as static files with the engine bundle: any static server over it serves the editor, ?host=worker runs it with no program; --site is the whole website with the editor in it, --page only the page (a heavy job)
cargo xtask regen                           # write every generated file again (page contract, docs): after a rebase stops on one, take either side, then this
```

`lib:` paths read `library/` from disk: this checkout's when run inside it (new and edited library tiles count at once, no rebuild), else `$DT_LIBRARY`, else the copy installed beside the program. Nothing is compiled in.

Output goes to `out/` (git-ignored).

CI is off. Run the tests locally on this Mac only; do not wait on or re-enable GitHub Actions. Linux, Windows and cross-OS hashes are a later stretch goal.

## Spatial Terminology (canonical — do not deviate)

| Level | Name | Size | Key symbols |
|---|---|---|---|
| Full printed output | **tile** | cols × rows × square_mm | `tile` node, `Frame`, `out/` |
| One 35 mm DungeonBlocks unit | **square** | 35 × 35 mm (or 25.4 for OL) | `cols`, `rows`, `perSquare` |
| One heightmap subdivision | **cell** | square_mm / cells_per_square | `Frame::step_mm`, `Field` |

**Never call a 35 mm unit a "tile".** Densities are `perSquare`.

## Architecture

Sixteen crates under `crates/`:

| Crate | Role |
|---|---|
| `dt-lang` | The language's word tables, no dependencies: functions and their arities, weightings, coordinates, unit words, `$` names, land slope and water settle, the registry of diagnostic codes (`codes.rs`: every `dt::…` code, once), and the registry of every word (`words.rs`: one `Word` row per word of the tile language and the program, with its one meaning and kind; vocabulary tests in dt-lang, dt-doc, dt-service and the program hold the decoder, the schema, the verbs, the commands and the flags to it). Read by the decoder, completion, the docs generator, the elements and the page (via `/api/language`). |
| `dt-value` | What a document's numbers draw from, no geometry and no dependencies but `libm` and `dt-lang` (for the diagnostic codes): keyed seeds and the seeded stream (`Seed`, `Rng`), and weighted ranges (`Weighting`, `Dist`, `Draw`: a range's odds, one draw, any width). `dt-geom` and `dt-kit` read it; it reads neither. `Canon` and `Canonical` (canon.rs) are the one canonical writer every key is made with (a value is tagged, a float is its bits; the step cache, a tile's key and a thing's key all write through it, each crate writing its own types where they are defined). |
| `dt-geom` | Kernels: mesh backend (Manifold via `manifold-csg`), rays (obvhs), the terrain's stack mesher (`stack`, built on the adaptive lift), keyed noise, grids, distance transform, adaptive lift, convex hulls. No element knowledge. |
| `dt-kit` | The vocabulary elements are written in: `Scene` of tagged solids, `Field` and its morphology, `scatter`, `loft`, `extrude`, `carve`, `union`, forms (level sets, hulls, relief), graphs (trees), `stand`, rays, the audit gate (`audit`), the build record, and the painter (`Palette`, `paint_mesh`: a colour for every face, which the editor and the browser show). Printing is not here. `things.rs` is a thing built once: a `Body` (meshes in the thing's own frame, no slots), `Body::set_down` (the one path from a body to solids in the scene: a slot for each part, turned about z, stretched up, moved), a `ThingId` (the canonical form of everything a body is made from), `Bodies` (one build's: a body is asked for by id and a way to make it, answered from the build's memory when a variant made it already, else from the `Shelf`, else made and put on the shelf; counted in `ThingUse`: built, shared, kept) and the `Shelf` trait the store implements, so the engine knows nothing of disks. |
| `dt-elements` | The built-in elements, each written only in `dt-kit`'s public operations: `ground`, `dirt`, `rock` (and `stone`, `boulder`, `pebble`, `flower`, `scatter`), `water`, `grass`, `reeds`, `cliff`, `wall`, `floor`, `tree`, and the DungeonBlocks / OpenLOCK connectors. Two kinds of generator: a **layer** (`Element`: reads the scene so far and changes it) and a **thing** (`thing::Thing`: its controls and a seed make solids in its own frame, reads nothing). The frame rule: the origin is where the thing meets what holds it, +z points away from that surface, +x is its main axis (`Thing::make`). A thing reports its `extent` (the smallest and largest box it can draw, from its own range ends, reference mm), how it `meets` the ground (bedded: rocks; dry: flowers; upright: trees; data the placer reads, never matched by name), and what a scatter of it `usual`ly uses (`gap`, `perSquare`, `reach`: a mix takes its first child's). `Rock`, `Plant` (flower) and `Tree` implement it; the one `thing::Scatter` places any list of them: each item draws its child by `weight` and its size from its own keyed seed, the draws of one family are placed together (one dart-throw, `thing::place_group`) and stood into the scene as one batch (`Thing::stand`), the family whose largest extent reaches farthest first, each clear of the discs before it. `at=foot(…)` gathers only things that `gather` (rocks: scree). A new thing is one `impl Thing` and a row in `thing::THINGS`; there is no other scatter. How the places fall is one `thing::Shape` (`pattern=` spaced, clumped or cover, clumps, `cover`, `clearings`) read by the one dart-throw as its density, its darts and whether the things keep apart (`Spread::apart`; a cover checks no spacing among them and stays linear in the number of things); `near` (`of=` rock, wall, tree, cliff, standing, water) measures each placed item's distance to what the scene held before the scatter (one `Nearness`) and within a reach drawn for it leaves it out (`thin`) or hands its thing a `Standing::tall` (`height`; only a thing that `grows_tall` takes one: rocks, flowers). A rock is built in its own frame and set down by `Body::set_down` (`rock.rs`: `stone_id`, `stone_body`, `stone_of`; the id is the stone's hull and the seed of its grain), the only path from a rock to the scene, so `make_with` and `stand` are one; `Ctx::things` is the build's `Bodies`. `scatter variants=K` draws each placement as one of K variants (the item's own stream picks which; the variant is drawn from a stream keyed by the child and the variant, so every copy is the same draw), `Drawn::of_variant` carries it and a variant's body is held for the rest of the build, built once. Flowers and trees are built where they stand (`Plant::meshes` and `Tree::grow` at the place): a flower built at the origin and moved differs by a hair's breadth, which moved 1x1-grass-flowers' pinches past their budget, and a tree's sink, footing and `top=` read the tile, so neither is kept as a body and `variants` on them only limits the shapes. |
| `dt-doc` | KDL v2 documents: decoding with spans and `miette` errors, the element schema (`elements.rs`: controls, and each element's body, footprint, family and cost; `schema::Generator`, thing or layer, is derived from the role, so there is no second table: a thing is what a scatter may hold, and what a `param` may hold, which `Value::Generator` and `Callee::Param` carry through the decoder, `ParamInfo::thing` to a caller's `leaf=boulder`), one expression evaluator (`Expr::eval` over an algebra), the one kind system (`units::Kind`: plain, length, angle, region, point, and the two generator kinds `Thing` and `Layer`, with `units::fits`, the one answer to whether a value of one kind fits where another is wanted, and `units::misfit`, the one wording of a kind mistake; every check site asks them, and `tests/generators.rs` scans for any other; `Kind::WORDS` is the table `kind=` reads; a thing fits where a layer is wanted because placing makes it a layer, a layer never fits a thing; `Definition::generator` is a thing only when its stack is exactly one unplaced thing; a `param`'s `kind=`, default and uses are settled in `Decoder::param`, and a written number kind is a control it fills, `elements::kind_control`), the edits: `ops` for a `.dtile`, a print list and an inventory (`Op` through one `apply`, by node or piece id, one `EditError`; a tile's nodes are named by `nodeid`, e.g. `tile/stack/rock#2`, and every `.dtile` edit writes only the byte ranges it changes). |
| `dt-eval` | Reads a document (the reader resolves a thing or layer param (`param ground dirt`, `kind=layer`: a layer param is only an entry, a thing fits it) to its element or definition in the file its caller wrote the name in, `Resolved`: the properties written on that entry are kept as written, `Callee::Param`'s `GeneratorParam`, and typed there by `dt_doc::decode::bind_generator`, the decoder's own `control` function run again with the element or definition as the callee, so a property gets the checks, the codes and the words it gets written on the thing itself, group sub-controls included; a definition's param written there as a value (`piece size=s`) is told its control in the same step, `reader/late.rs`: the call's argument for it, and its default, were kept as written, `Late`, and are typed by `dt_doc::decode::type_late`, the decoder's own `value`, so they get the same checks as on the element, pointing at the call's argument, and a param that fills two controls that are not alike is `dt::type` at the param), plans it (`plan.rs` orders the stack by what each element reads and writes), builds it into a `Scene`, audits, and returns the build. `thing_build` draws one thing alone: `subject` finds the thing a document means (a `define` by name, read by the reader as a one-entry tile that calls it, or one entry or one child of a scatter by its id) with its controls as the reader made them (a tree's `top=` is read with `$bottom` at zero: alone it stands on ground at zero), and `Subject::draw` makes one draw at a seed with `Thing::make` and joins and gates it with the same `build::join` and `build::gate` a tile's build uses (by tier: full is the union and the audit's overhang paint, low and draft are the parts as they are and the angle alone), as a `Built`; it is not kept (a thing has no key of its own yet). Printer profiles (the gate's floors and the machine) are read here, since a build's gate needs them. Library tiles are bundled from `library/`. |
| `dt-par` | Parallel iteration for the engine: rayon everywhere but the browser, where the same calls run in order. |
| `dt-service` | The editor's service below every transport: the owner of the editor's state (`Core` with its typed `Command`s, driven by `Core::apply`; on native a thread loop over a channel, the `Owner` handle), the event stream (`Events`), the roots and their scans, the build queue and the tier book, generic over a `Host` (the transport's jobs, failures, alarms and time), and the verb table (`call.rs`: a verb and its typed request to a typed answer); the `Storage` trait for every file the editor reads, lists, writes, deletes and trashes (with `Entry` and an in-memory `MemStorage`), the `Clock`; the page's wire types (`api`, `plan`, `scene`, `resources`, `message`, `stack`, `inventory`: the types `web/preview/js/api.d.ts` is generated from); a tile's state (`Slot`, `Row`, `Facts`) and the typed `Patch` that changes it. It depends on the engine crates (`dt-eval`, `dt-kit`, `dt-doc`, `dt-print`) and `dt-value`, reads no disk, knows no HTTP, and builds for `wasm32-unknown-unknown` (`cargo xtask wasm --check` holds it); `tests/no_server.rs` runs it on `MemStorage` and a test host. `tile_calls`, `edit_calls` and `build_calls` hold the tile calls that need nothing of a transport: `check`, `edit`, `save` and `build`, each with its types and one function the HTTP handler and the worker's `Service` both call, written on `TileHost` (`tile_host.rs`: the host's `docs()`, `storage()`, `library()`, `want(id)` and, through `CheckHost`, `options()` and `report()`). A call's refusal is a typed `call::Refusal` (a `Status`, a fault, causes, the conflict's text and revision, a document's mistakes) that each transport maps (HTTP: `api::refusal_reply`); `docs.rs` is the documents' revisions and lock (`Docs`, told of each write by the host). `build` is one verb with one meaning: it queues the job and the record comes on the event stream. `header` and `payload` are the mesh payload the page reads (`MeshHeader`, `encode`, `from_built`, `from_draft`, `for_map`, the debug marks and clouds): the binary's lanes and the web worker's builds make the page's mesh bytes with the same code. `draft_calls` is `draft` and `step` (an edit and the draft of what it made), written on the host's draft lane (`TileHost::draft`: the program queues the draft ahead of its builds and waits, the worker builds it in its turn); `read_calls` is what reads a text without building it (`names`, `tokens`, `checkValue`, `printed`, `printedSet`, `offers`) and what the page reads at startup (`about`, `elements`, `language`, `text`, with `elements_json` making the schema's JSON); `place_calls` is `newTile` and `mine` (My tiles and the listing of what was written are the host's: `TileHost::home`, `listed`); `folder_calls` is the places' own calls (`newFolder`, `renameFolder`, `trashFolder`, `trashTile`, `undoTrash`, `moveTile`, `duplicateTile`, `rename`, `deleteTile`) on `PlaceHost` (the places, the Trash, the rescan and the stream's revision, `moved`: whatever the host keeps by path follows a tile), deciding once what a call may touch (a folder place the user owns, never the library, no `..`, the real path inside its place: `Storage::is_inside`); `target_calls` is `setTarget` on `TargetHost`; the host also gives `version` and the first `snapshot`. A `Refusal` carries a bug's help and backtrace, the `superseded` mark, the `conflict` (the file as it is now and its revision) and what the program was `doing` (`Refusal::doing`: the lane's work, the draft worker, for the error's context), and `Refusal::reply` is the error body HTTP sends, which a worker tells the page too. `list_calls` (`listsNew`, `listsAdd`, `listsCount`, `listsRemove`, `listsRestore`, a list's `check`) and `map_calls` (`mapsAdd`, `mapsSet`, `mapsBatch`, `mapsDup`, `mapsRemove`, `mapsPin`, `mapsUnpin`, `mapsUnpinAll`) are the print list and map edits on `ListHost` (a `SceneHost`, which reads a map as a scene with no geometry (`scene_read`), and a `PlaceHost`), with `placing` (the nearest free square, a fresh seed); the web worker answers them too, and `dt_eval::Profiles` is the one question a printer profile's reading asks (the disk's `OnDisk`, the browser's `InSource`). `DiskStorage`, the build lanes, `Shared`, the folder chooser (`addPlace`, `removePlace`: a web page has no folder to point at) and the printers' slicer import stay in the binary. `export_calls` is `exportTile` and `platesExport`: the files' bytes are made once (`dt_print::tile_files`, `plate_files` over `Builds`), the program writes them where `dharmatiles build` does and the browser editor's service answers them as `Download`s (a name, a media type, base64 bytes) that the page saves through `host.saveFile`; a plate set is `bambu`, `stl` or `3mf` as the caller says (a Bambu project needs a template file, which `PlatesHost::bambu_template` finds in the program and refuses by name in a worker). `tier_calls` is `tiersWant` (the types, the key, `prepare`, `tier_bytes`; the program queues each tier on its lane, the worker builds them in the call and says the same on the stream) and `tierResult`; `message_calls` is `messages` (the text) and `messagesReport` (`report::of`, the one producer of a defect's issue). Every call of the page's contract is a service verb, the worker host's own (the stream, a mesh, a sketch: none while a build runs inside one call, the page's report) or the program's alone (`program` in `worker-calls.js`: a folder chooser, the file manager, the slicers). `plates_calls` plans a print list or a map (`rebuild`: its scene, crowns and plates, as patches the owner takes; `platesShow`, `platesSet`) on `PlatesHost` (the owner's patches, the builds, the files' times, the host's own clock): the program builds on its lanes and disk cache, the worker in its own turn. `inventory_calls` is the inventory: the one reader and writer of `inventory.dinv` (`load`, `append`, through the host's `Docs` over its `Storage`: the disk in the program and the command line, the store in the worker), whether a tile changed since it was printed, the snapshot's `InventoryState`, an opened `.dinv`'s `rebuild`, `note_rename` (a moved tile's prints follow it) and the verbs `inventoryHave`, `inventoryRecord`, `inventoryGone`, `inventoryRelink`, `inventoryReprint`, on `InventoryHost` (a `PlatesHost` that also knows today's date, says a message and gives a list's plan); `SceneHost::entropy` is where a fresh seed's randomness comes from (the system in the program, what the page gave in the worker). `thing_calls` is `buildThing` on a `PlatesHost` (for its palette): `ThingReq` (`text`, the page's text of `file` or, with none, of the tile, laid over what the host stores as a check's is; `which`: a `define` by name, read from `file` when there is one, or an entry by its stack key with a scatter's child, always read from the tile, so a called part's thing is an entry of the tile; the `seeds`, and a `tier`) answered by `ThingRes` (the element, its controls as built, the extent as the smallest and largest box in printed mm and in dmm, one `ThingDraw` per seed: its triangles, its own box, whether the gate checked it and the page's mesh payload, `payload::from_built`, as base64, and `used`, the `ThingUse` of the call's bodies, and `problems`, what went wrong with the shelf, which the page shows as a failure); a rock's body is kept on the host's shelf (`PlatesHost::thing_shelf`: `dt_store::Shelved` over the program's disk store or the worker's `MemStore`; `dt_kit::Bodies` per call), so a seed drawn before is read; `Thing::extent` is the box of one thing alone (what `make` builds: the editor shows it and `the_extent_bounds_every_draw` holds it for every word of `THINGS`) and `Thing::placed_reach` the disc a draw asks of a scatter (what placement orders by); refusals are typed (no such define or entry 404, a layer or a mistake 422, no seed 400); the program's route and the worker's `Service` both call `build_thing`, and `tests/thing-parity.json` is the golden both halves of `parity --service` hold the draws to. Its `inspect` feature (a test's look inside the owner) is turned on by dharmatiles' dev-dependencies alone: only the program turns it on (dt-web depends on dt-service without it), so like the crash switch it builds twice only itself (about 3 s) and the binary, nothing below. |
| `dt-store` | The disk cache of builds: a finished `Built` kept under a SHA-256 key (the `sha2` crate, over `dt-eval`'s canonical form of everything the build read), and the one stored-build function, `build_stored` (every tier, through the `Kept` trait: what keeps a build). `Kept` is implemented by `Store` (the program's disk cache) and `MemStore` (the browser worker's memory, the same entry bytes, bounded by one limit with the least recently used out, no clock and no disk, so it builds for wasm; a `Watcher` hears every `Change` and `load` takes entries back, which is how the browser keeps builds between visits); the program's build lanes, the CLI, the plates, the poster and the worker all call `build_stored`, and no caller builds through `dt_eval::build_cached` beside it (that is the engine's inner call, under `build_stored`; drafts pass no store). `make_key` is the one key maker: `build_stored` calls it with the store's engine, and the browser engine (`dt-web`'s `stored_key`, compiled into the wasm) makes the parity run's key with it, so no key is made in JavaScript. A document's path is part of the key, so every build of a tile (the lane's, an export's, a plate's piece) names the tile's own path, never a stand-in. A thing's body has its own key from the same maker: `make_thing_key` (`key_head` and `keyed` are shared with `make_key`: the format, the engine, the tier, the target's system and printer, then the thing's kind and its canonical bytes), kept as an entry of the same store through `Kept::get_body` and `put_body` (a body is written without a sync and the folder is brought under its limit once, by `Kept::settle`, when the build is over), and `Shelved` is the one call that makes a `Kept` store the engine's `Shelf` (`Bodies::new(Some(&Shelved::new(&store, &opts)))`); `build_stored` does it for every tile it builds, and the build record's `things` says how many were built, copied and read. It sits above `dt-eval`, which knows nothing of it. |
| `dt-print` | A built tile on its way to a printer, above the engine: print lists, plates and the packer, the inventory, binary STL, 3MF and Bambu Studio projects. `tile_files` makes the bytes of a tile's STL, record and 3MF, and `plates::builds::Builds` (build every piece, lay out, make the files) makes the plates, for `dharmatiles build`, the program's Export and the browser editor's service alike. |
| `dt-render` | The CPU renderer that draws `build --png`, the contact sheets and dt-eval's golden pictures. A crate of its own so that a change to printing does not select the engine's tile tests. |
| `dt-crash-switch` | The crash switch the CLI's exit-code tests drive (`DT_TEST_PANIC`), a leaf only the program depends on: its `on` feature is turned on by dharmatiles' dev-dependencies alone, so it reaches this crate and the binary and nothing else (a test-only feature anywhere lower would build every crate above it twice). |
| `dt-testkit` | What the tests share, a dev-dependency only (the program does not carry it): `build`, one build of a document kept for everything the build reads (the source's content, the path, every field of `Options`), so a test run never builds the same tile twice. dt-eval's, dt-store's and dharmatiles' tests use it. |
| `dt-web` | The browser build (`cargo xtask wasm`): the language crates and the engine on `wasm32-unknown-unknown`, left out of a plain `cargo build`. `service.rs` is the editor's service in a web worker: `Service` (`put`, `set_target`, `call(verb, tile, requestJson)`, `built(path)`, `events()`) over a `MemStorage` and an owner `Core`, answering by verb (dt-service's own functions, on a `TileHost`): `check`, `edit`, `save`, `build`, `names`, `tokens`, `checkValue`, `printed`, `printedSet`, `offers`, `buildThing`, `about`, `elements`, `language`, `text`, `mine`, `newTile`, the folder and trash verbs, `rename`, `deleteTile`, `setTarget` (the system; ### How a build runs

`document -> dt-doc (decode, check against the element schema) -> dt-eval::check (plan) -> build each element into the Scene, in the order the stack is written -> union -> audit -> STL`. Stack order is build order: grass sees the rocks listed before it, water fills over what is under it. An element says what it writes in `Element::plan` (a surface, a fill, a laid layer or a solid); the plan refuses a stack whose entries need something nothing earlier made.

Every leaf solid takes a slot reserved in sequence, so its source id (and so the material of every output triangle, and every hash) is fixed by index whatever thread builds it. Builds are identical whatever the threads; the `tiles` test binary builds each test tile once, on two threads with progress, sketches and the debug layer listening (`crates/dt-eval/tests/tiles/memo.rs`), and holds its stage hashes to insta snapshots recorded from plain builds (`crates/dt-eval/tests/tiles/golden.rs`, snapshots in `crates/dt-eval/tests/tiles/snapshots/`): a match is the proof that threads and observers change nothing. A test that builds a `lib:tests/` tile at its default options reads `memo`'s build, never builds it again.

### Tile documents

```kdl
tile size="1x1" seed=97 {
    line shore wobble=5 { through "0,0.38" "1,0.42" }
    region pool { boundedBy shore; fill "0.5,0.25" }
    region bank { boundedBy shore; fill "0.5,0.75" }
    stack {
        dirt at=bank
        grass at=bank
        ground at=pool level="water - 2.2"
        scatter at=pool count=2 { rock size="6..10" }
        water
    }
}
```

Lines and fill points make regions; the stack paints surfaces (`ground`, `dirt`, `floor`, `water`) and stands things on them (`rock`, `scatter`, `grass`, `reeds`, `wall`, `tree`). Sizes are mm at the 35 mm square and scale with the system. Read `docs/language.html` (the map of the guide) and the concept pages under `docs/guide/` for the language, and `docs/elements/` for each element.

### Library

`library/tiles/<group>/…dtile` are the shipped tiles (the Library tab, `build --all`); `library/tests/<group>/…dtile` are the test tiles (the Tests tab): the tiles the test suite builds, kept apart so library tiles can come and go without touching the tests, and free to be odd shapes and edge cases no library would ship. Of them, the **torture set** (`golden::TILES` in `crates/dt-eval/tests/tiles/golden.rs`, about 30 small tiles chosen by measured line coverage of the engine) is all the warm check builds; `library/parts/` are shared definitions (`grass`, `trees`, `edges`, `levels`).

## Standing rules

- **Overhang is red.** 55 degrees is every element's target. 55-65 degrees is the band, painted orange, allowed up to 0.1% of the downward-facing area; over 65 is red, allowed up to another 0.1%; more fails. Both angles are the printer profile's `overhang` and `steepest` (library/printers/default.dtile). The printability gate is a gate: never loosen a threshold or cull geometry to pass it; fix the geometry where it is made.
- **Errors: nothing swallowed, nothing hidden.** Expected errors (a document mistake: a `dt::` diagnostic with span and help, or a gate verdict) are shown where the user made them; unexpected ones (panics, I/O, kernel failures, server errors) travel up with `?` to a boundary (CLI main, preview route, build worker, page handler) and are shown loudly, never only logged. No `let _ =`/`.ok()`/`unwrap_or_default()` on real failures, no fallback that silently changes output. The few allowed silences (localStorage, best-effort cleanup, user cancel, offline retry) carry a comment. Every diagnostic code is made once, in `dt-lang/src/codes.rs`, and used by its constant (a test fails on a `"dt::…"` literal anywhere else); a new code needs a registry entry and a `data-explains` marker on the docs section that explains it (`cargo xtask docs` then writes its `e/<code>.html` page and anchor). See `docs/standards/errors.html`.
- **One typed model.** Every piece of data has one definition: a Rust type with serde in the lowest crate that owns it, made by one constructor, read by deserializing it, and when the page or site reads it, its TypeScript type generated from it (ts-rs, `web/preview/js/api.d.ts`). Never build a record from `json!` literals for someone to read back, read by string key (`v["audit"]["triangles"]`), hold structured data as `serde_json::Value`/`JsonValue`, hand-write a mirror (a second struct, a JS shape, a test struct, a column list), or make a field optional because some copy omits it. A file format is read and written in one place, on its type. A build's result is `dt_eval::TileRecord`, its gate verdict `dt_kit::AuditSummary`. See `docs/standards/rules.html`.
- **The language rules.** dharmatiles keeps the language principles (`~/.claude/skills/language-design/principles.md`) with these, which the global skills and Orin read from here:
  - **word registry:** `crates/dt-lang/src/words.rs`; a new word is a row there, and its vocabulary tests fail on a word used and not registered, registered twice, registered and unused, or doing two jobs;
  - **ledger:** `ledger.kdl` at the root, read only by `dt_doc::ledger` (`Ledger::expect` is the shrink rule); `cargo xtask check`'s ratchet (`xtask/src/ledger.rs`) refuses an added id outside a commit that touches `ledger.kdl` alone, and `cargo xtask release` wants such a commit since the last tag (or `--skip audit "<reason>"`); every added line is probed by whoever commits it and confirmed by an Orin agent that did not find it, with the id and probe in the commit message;
  - **closure and check equals build:** `crates/dt-eval/tests/tiles/closure.rs` (kinds from `Kind::WORDS` by `Form`; a cell works, is a refusal the rules call for, or is a `hole:` line);
  - **surfaces:** `.claude/language-surfaces`, the files whose edit makes the edit hook remind of the design check.
- **KDL is v2 only.**
- **One visual system.** The docs site and the preview share `docs/assets/theme.css` (tokens, self-hosted fonts, lotus, controls); the preview serves it from inside the program. New colours, fonts or controls go there, never into one page or the preview alone. On a model red and orange mean overhang (`--over`, `--band`); the interface's danger red (`--err`) marks errors and destructive actions, a separate token; tiles are shown on the plate (#D9E0EB). See `docs/standards/visual-system.html`.
- **Docs are HTML** under `docs/`, never `.md` copies; lead with what a tile user needs; no commercial product images.
- **The site is current state only.** It says what the program is and does now: the reference, the specification and the rules. No decision logs, histories, rulings with dates, lab write-ups or reference-photo galleries; git history holds how we got here. The one exception is the changelog, `docs/changelog.html`, a hand-written static page (no feed, nothing generated); each change not yet released is its own file, `docs/changelog.d/YYYY-MM-DD-HHMM-some-words.html` holding one `<li><strong>What changed:</strong> …</li>`, added as it lands (two branches never edit the same lines; `docs --check` refuses a misnamed one, or an Unreleased entry on the page); only when Shawn asks for a release are those folded, newest first, into an entry with a number and date and `version` in `Cargo.toml` get bumped, always with `cargo xtask release <version> "<summary>"`, which also tags every release `v<version>` (`--skip tests "<reason>"` while a known test failure stands; `--skip audit "<reason>"` with no recent audit). When a rule changes, update `docs/standards/rules.html` (project-wide), the element page's Rules list, or the language guide's rules, in place. The Rust code is the reference for how things are implemented; pages link to it rather than restate it.
- **The site is the tile language's reference.** `docs/language.html` is the map of the guide and `docs/guide/<concept>.html` are its concept pages (every code sample on them is a whole document `cargo xtask docs --check` runs through the program, or marked as a fragment; the cheat sheet, the margin lists, the old-anchor redirects and each rule's "errors this page explains" are generated); `docs/elements/<name>.html` is one page per element (every node a document can write). The code uses the same word: the `Element` trait, the `dt-elements` crate, the element schema in `dt-doc/src/elements.rs`. Each element page's controls block is generated: run `cargo xtask docs` after changing an element's schema, and add a page for any new element (the generator refuses an element without one). The preview links each stack entry to its element page.
- **Pronouns:** use they/them for Shawn.
- **Contact sheets:** make one with `cargo xtask sheet` and look at it yourself at full resolution before calling an element done. Element pictures come from `cargo xtask pictures`; look at them too.
- **Keep the loop fast.** Budgets: a warm build under 1 minute, `cargo xtask check` under 2, a cold build under 5, `cargo xtask check --full` (before a push or a release) about 10. Every `cargo xtask` command, and each step of `check` (the build is a step of its own, held to the warm or the cold build's budget), is timed against its budget in `xtask/src/budget.rs` (the one table), prints its time, logs it to `dt-times.tsv` in the git common folder and prints an OVER BUDGET banner on both streams when past it. When a cycle is over budget, the next task, straight after the current one and ahead of the queue, is to make it fast again; say so on the Bench. Fix the waste where it is made, never by skipping a check or loosening the gate.
- **A test never builds what a test already built.** dt-eval's integration tests are one binary (`crates/dt-eval/tests/tiles/`, a module for each file) and build only through `memo::build`, which keeps one build for everything it reads (the source's content, the path, every field of `Options`); `memo_only` fails a build that skips it unless a `// fresh: why` comment says the test must build again (the cache, thread counts, a build compared with itself). dt-store's and dharmatiles' tests use the same memo (`dt-testkit`) where a test is not about the build or the store itself. A warm test reads only the torture set (the memo fails one that reads another test tile); a test that needs another tile is a `thorough_` test (ignored, its reason saying so), which `cargo xtask check --full` runs with the library sweep in one run. A new element or feature gets a small torture tile, and a test of it reads that. A test that builds fresh passes its options through `dt_testkit::seeded`, so `DT_TEST_SEED` reaches it too (the `memo_only` scan fails one that does not).
- **Builds are heavy; the machine has 12 cores.** At most two agents at once, each with a task that lands in under about 45 minutes. Sweeps, contact sheets, pictures and the browser engine go through the heavy-job lock (`cargo xtask sweep`, `sheet`, `pictures`, `wasm`, or `cargo xtask heavy <command>`), so two never overlap. Merge on `cargo xtask check`; run `cargo xtask check --full` once before a push.
